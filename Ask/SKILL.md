# Ask（技能路由）

本机全部已装技能的路由器。**以会话中 system-reminder 实时列出的可用技能为准**；本文件的清单可能滞后，与实时列表冲突时以实时列表为准。不凭记忆编造技能名。

路由到目标后：**立即用 `Skill` 工具加载并按其指引执行**。只给建议、告诉用户“请使用 xxx”、等用户手输斜杠命令，都算路由失败。

## 何时使用

- 任何会话与任务开始前：先做技能检查，再行动。
- 不确定当前任务该用哪个已装技能。
- 用户请求横跨多个领域，或任务类型模糊。
- 用户提到“该用什么技能 / 流程 / skill”。

不使用：纯闲聊、无任务意图的对话 —— 没有任务就没有路由对象。

## 调用纪律

以下规则适用于任何会话与任何任务。

| 规则 | 内容 |
|---|---|
| 1% 规则 | 只要有任何可能适用某个技能，就必须调用它。不可协商，不能合理化跳过。 |
| 先调用后响应 | 在回应任何问题（含澄清问题）、探索代码库、检查文件之前，先完成技能检查。检查在前，其余在后。 |
| Process 技能优先 | 多个技能适用时，过程类技能先行，它定方法，实现类技能随后执行。“构建 X” → 先 `ProbeIntent` 再实现技能；“修 bug” → 先 `Debugging` 再领域技能。 |
| 用户指令优先 | 用户指令 > 技能 > 默认行为。用户明确要求跳过技能流程时跳过。 |
| 技能会演化 | 用时读当前版本，不凭记忆。 |

### 合理化红牌

发现自己在想左列，即停止该推理，先查技能。

| 想法 | 现实 |
|---|---|
| “这只是一个简单问题” | 问题也是任务。先查技能。 |
| “我需要更多上下文” | 技能检查在澄清问题之前。 |
| “我先探索一下代码库” | 技能告诉你如何探索。先查。 |
| “这不需要正式技能” | 有技能就用。 |
| “我记得这个技能” | 技能会演化。读当前版本。 |
| “技能小题大做” | 简单的事也会变复杂。用它。 |
| “我先只做这一件事” | 行动前先查。 |
| “这感觉像是在推进” | 无纪律的行动是浪费时间。 |

## 路由方法

1. **归类意图** —— 在下方路由表找到对应分组。
2. **选最贴合的具体技能** —— 同名或同源时优先用户级（无前缀）版本。
3. **`Skill("技能名")` 加载执行** —— 把路由结果变成行动，而非建议。

标注 `（插件）` 的技能来自插件生态，不在 `~/.claude/skills/` 下；其余为本地用户级技能。路由规则对两者相同。

### 关键词判定

任务意图模糊时按关键词计数分类：

| 行为带 | 关键词 | 去向 |
|---|---|---|
| 构建类 | 开发 / 创建 / 生成 / 构建 / 搭建 / 实现 / 写一个 / 从零 / 做一个 / 新项目 / 脚本 / 工具 / 应用 | 执行类技能（`ExecutingPlans` / `TDD` / `run` 等） |
| 修复类 | 修复 / 调试 / 重构 / 排查 / 报错 / 崩溃 / 优化 / 维护 / 迁移 | 计划类技能（`Debugging` / `WritePlan` 等） |
| 计数相等，或无命中关键词 | —— | 不强判，走模型自分类 |

模型不能可靠自路由，有效的内部路由窗口是弱 persona + few-shot。因此本判定只做倾向性分类，不武断翻转任务类型 —— 这就是 1% 规则的量化版。

## 禁用与歧义消解

- **已禁用技能**：`[已禁用]` stub 或 `skillOverrides: "off"` 的技能任何时候都不路由。已合并而禁用的技能同样不路由，只路由本表当前的名字。
- **多技能同时适用**：逐个按序加载执行，不要只选一个。例如“写完想审查” = `PolishCode` + `ReviewPr`。
- **表中找不到匹配**：用 `SkillstoreFetch` 搜索可安装技能，或直接以普通方式执行任务。

## 红线

- 只路由到**真实存在**的技能。本表未列出、且不在实时列表中的技能名，一律视为不存在。
- 路由不等于建议：选中技能后必须**立即用 `Skill()` 加载执行**，不得停在“建议”层面。
- 不把用户当操作员：全程由 AI 自己加载技能。
