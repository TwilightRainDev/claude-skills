# WriteIssue（issue 起草）

写 issue 不是打字，是把回答者需要的证据按顺序摆好。流程四步：**搜索门禁 → 面试式追问 → 起草 → 自查**。

纪律核心一条：**不编造** —— 发出去的每一个字都必须来自用户提供的信息，或带 [待补充] /「推测」标记。

前置知识：假定你理解“最小复现”与“XY 问题”。

## 何时使用

- 用户要写 GitHub issue / bug report / 向项目反馈报错
- 用户拿到报错，想发帖求助开发者
- 同样适用于 Stack Overflow、论坛、Discussions 的提问

不使用：
- 内部工单 / 企业流程（审批链不同，不适用公开社区礼仪）
- 用户只是想口头讨论问题，明确不需要对外输出
- 聊天式答疑（用户没说要写帖）

## 核心流程

### 第 1 步 —— 搜索门禁（先问，再写）

发帖前一次性问清（可多选追问，不要挤牙膏）：

1. 你在目标仓库的 Issues / Discussions 里搜过关键错误词吗？
2. 搜索引擎（谷歌/Bing/百度）查过吗？
3. 官方文档 / FAQ 读过吗？
4. 喂过 AI 吗？AI 给了什么建议、你试了哪些？

- 用户说“没搜过” → 请他先搜，或明确告知“这个 issue 大概率会被以『已有人问过』关闭”。用户坚持跳过 → 在“已做功课”里如实写“未搜索”，不假装搜过。
- 用户说“搜过” → 把实际搜过的关键词写进 issue 的“已做功课”，作为证据。

### 第 2 步 —— 面试式追问（六要点简报）

追问纪律的通用形态（单问题推进、缺项占位、不编造）见 `CreatePrompts/references/interview-discipline.md`；本步是它之上的六槽位具体化。

按六个槽位一次性追问所有缺失项。**每个槽位要么有用户提供的信息，要么写 [待补充]，没有第三种状态。**

1. **目标**：你想达成什么？先问目标，再问方案 —— 防 XY 问题。
2. **环境**：OS+版本、运行时/语言版本、关键依赖版本、部署方式（真机 / VM / WSL / 容器，容器附镜像标签）。
3. **报错原文**：完整错误消息 / 堆栈 / 响应体 —— 要原文，不要用户转述。
4. **已做功课**：搜过什么关键词？文档读过哪章？试过哪些操作？
5. **复现步骤与时间线**：从哪个操作开始出错？近期改过什么（升级 / 环境变量 / 新服务）？
6. **实际 vs 预期 + 最小复现**：实际行为 vs 期望行为；最小代码片段 / Dockerfile / cURL（密钥脱敏）。

用户拒绝提供某项 → 该槽位写 [待补充]，继续，**不编造**。

### 第 3 步 —— 起草 issue

**标题配方**（≤50 字）：`[组件/版本] 现象描述`

- 好：`[Docker Compose v2.23] [WSL2 Ubuntu 22.04] bind mount 报 Permission denied`
- 禁：求助/救命/急/紧急/bug！/新手求问/“有人能帮我吗”
- 用户要求烂标题 → 换成描述性标题并说明理由（“这类标题会被直接过滤”），不照抄。用户坚持 → 给他换好的，让他自己决定发哪个。

**正文配方**（六要点模板，见快速参考）：核心报错放最前面，完整日志放末尾或省略；日志/代码/命令必须放进三反引号代码块；报错原文直接复制，不翻译成自己的话（除非附原文）；不贴手机拍屏，不用 Word/PDF。

**事实与推测分离**：事实区只放原文。推测区必须带标记 —— “我推测是 X（未验证）”。**从格式推断出来的东西（如从 ENOTFOUND 推断 Node/PostgreSQL）一律标注“推断”**，不得写成事实。

**语言决策**：
- 项目官方交流语言是英文 → 全文英文。
- 由 AI 生成/翻译的 issue → 开头加声明行，**声明行语言与 issue 正文一致**：
  - 英文正文：
    ```text
    Please note that these questions were generated with the assistance of AI translation, and I apologize in advance for any inaccuracies.
    ```
  - 中文正文：
    ```text
    本 issue 由 AI 协助起草，如有不准确之处请见谅。
    ```
**礼貌**：开头“请问/请教”，结尾“感谢阅读/谢谢你的关注”。不卑微（“我是菜鸟求求了”）、不空洞（“有人能帮我吗”）。

### 第 4 步 —— 自查（交付前逐项过）

- [ ] 标题无求助词、含组件与现象
- [ ] 目标在前（不是从“我的方案”讲起）
- [ ] 环境含版本号（或 [待补充]）
- [ ] 报错原文在代码块里，且未被改写
- [ ] 已做功课如实列出（搜过什么/试过什么/读过什么）
- [ ] 有复现步骤或最小复现
- [ ] 实际 vs 预期分开写
- [ ] 每个推测都有「推测/推断」标记
- [ ] **无任何编造项**（每一条信息都能溯源到用户或标注）
- [ ] 英文项目 → 英文 + AI 声明行
- [ ] 无“救命/求助/有人吗”式废话

## 常见错误 / 合理化借口

| 借口 | 现实 |
|------|------|
| “用户让我编的” | 授权编造 ≠ 授权撒谎。issue 发出去挂着用户的信誉，也挂着你的。 |
| “他很急，先发出去再说” | 急是用户的，信誉是他的。编造的 issue 一次复现失败就不会再被回复。 |
| “信息太少，我只能编” | 信息少 → 追问 + [待补充]，永远有第三种状态。 |
| “这样写更完整，像真的” | 完整 ≠ 真实。维护者照着复现失败，比你没写更糟。 |
| “用户就要这个标题” | 标题是唯一一次被阅读的机会。“救命”标题进垃圾箱，帮不了他。 |
| “他让我别问东问西” | 别问 = 跳过追问，不等于跳过诚实。 |
| “我推测的，但写成事实更顺” | 推测不标记 = 编造。读者无法区分，就会按编造处理。 |

## 红旗信号 —— 停止并重新开始

- 你正准备写下用户没有提供的信息（版本、环境、日志、已尝试操作）
- 标题里出现了 救命/求助/急/紧急
- 你还没问“你搜过了吗”就开始写正文
- “已做功课”里写了用户没做过的操作
- 一个推测没带标记就要进正文

**所有这些都意味着：回退，用 [待补充] 或追问代替编造。**
