# Debugging（调试）

系统性调试流程：先构建能变红的反馈回路，找到根因，再动手修。

## 何时使用

任何 bug、测试失败、性能回归、构建/集成问题 —— 在提出修复方案之前先走本流程分诊找根因。

## 铁律

**未经根因调查，不得修复。**

未完成根因调查就不得提出修复方案。随意修复浪费时间且引入新 bug，修补症状即是失败。违反本过程的字面规定，就是违反调试的精神实质。

## 七个阶段

在进入下一阶段之前，必须完成当前阶段。跳过阶段必须给出明确理由。

### 阶段 0：分诊 —— 一个 bug 还是多个？

七个阶段用于调试**一个**故障域。当多个故障同时发生时，首先判断它们是相互独立的问题，还是同一个原因的不同表现。

**三项独立性检验：**

1. **多个故障？** 只有一个 → 跳过此阶段，直接进入阶段 1。
2. **相互独立？** 修复一个后，其他是否完全不受影响，即不同的测试文件、子系统或根因？
3. **可并行？** 无共享状态，多个 agent 不会编辑同一文件、争用同一资源，也不需要彼此结论？

**以下情况不得并行：**

- 故障相互关联，修复一个可能连带修复其他 —— 应一同调试。
- 需要全系统上下文才能理解其中任何一个。
- 尚处探索阶段，还不知道什么坏了 —— 先诊断，后分派。
- agent 会相互干扰（共享文件、共享资源）。

**当故障确实独立时，为每个故障域分派一个子 agent。** 每个 agent 在其自身域内端到端地遵循本技能：构建反馈回路、寻找根因、修复、清理。它不继承你的上下文，你需要构造它所需的一切。每个 agent 的任务必须是：

- **聚焦**：一个故障域，明确命名（例如“修复 src/agents/agent-tool-abort.test.ts 中的 3 个失败”，而非“修复测试”）。
- **自包含**：包含它所需的错误消息、测试名称和文件路径。
- **有约束**：明确它不得触及的内容（其他子系统、共享文件）。
- **明确输出**：返回根因 + 变更内容，而非“已修复”。

并行分派的通用协议（单消息并发、四要素任务描述）见 `ReviewPr/references/review-protocol.md` 的“阶段 1”。

在**同一条消息**中派发所有 agent，以便它们并行运行 —— 一次响应中的多个 Agent 调用并发执行，每个响应中只有一个会顺序执行。

**当它们返回时进行整合：**

1. 阅读每个 agent 的根因和修复摘要。
2. 检查冲突：是否有两个 agent 编辑了同一代码？
3. 运行完整套件，所有域一起，一次性通过。
4. 抽样检查：agent 可能犯系统性错误。

**常见分派错误：**

| [FAIL] 过于宽泛 | [OK] 聚焦 |
|---|---|
| “修复所有测试” | “修复 agent-tool-abort.test.ts” |
| “修复竞态条件” | 粘贴错误消息和测试名称 |
| 无约束，agent 重构一切 | “不得修改生产代码” / “仅修复测试” |
| 输出模糊，“完成” | “返回根因 + 变更” |

### 阶段 1：构建反馈回路

**这才是本技能的核心**，其余都是机械操作。如果你有一个**紧致**的针对该 bug 的通过/失败信号 —— 即针对*这个* bug 能变红 —— 你就能找到原因：二分法、假设检验和插桩都只是消费这个信号。如果没有这个信号，盯着代码看再多也没用。

在此投入不成比例的努力。**要激进。要有创造力。拒绝放弃。**

#### 构建方法（大致按以下顺序尝试）

1. **失败测试** —— 在能触及 bug 的任意接缝处（单元、集成、端到端）。
2. **Curl / HTTP 脚本** —— 针对运行中的开发服务器。
3. **CLI 调用** —— 使用固定输入，将 stdout 与已知正确的快照进行 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）—— 驱动 UI，对 DOM/控制台/网络进行断言。
5. **重放捕获的 trace。** 将真实的网络请求/载荷/事件日志保存到磁盘；通过代码路径独立重放。
6. **临时测试工具。** 启动系统的最小子集（一个服务，模拟依赖），通过单次函数调用执行 bug 代码路径。
7. **属性 / 模糊测试循环。** 如果 bug 是“有时输出错误”，则运行 1000 个随机输入，寻找失败模式。
8. **二分测试工具。** 如果 bug 出现在两个已知状态（提交、数据集、版本）之间，则自动化“在状态 X 启动，检查，重复”，以便使用 `git bisect run`。
9. **差分循环。** 对同一输入运行旧版本 vs 新版本（或两种配置），并 diff 输出。

#### 收紧循环

把循环当作产品。一旦有了*一个*循环，就**收紧**它：

- 能否让它更快？（缓存设置、跳过无关初始化、缩小测试范围）
- 能否让信号更锐利？（断言具体症状，而非“未崩溃”）
- 能否让它更确定？（固定时间、随机种子、隔离文件系统、冻结网络）

一个 30 秒的不稳定循环，比没有循环好不了多少；一个 2 秒的确定性循环，则是紧致的 —— 那是调试的超能力。

#### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。将触发循环 100 次、并行化、增加压力、缩小时间窗口、注入 sleep。50% 复现率的 flaky bug 是可调试的；1% 则不可。持续提高复现率，直到可调试为止。

#### 当你确实无法构建循环时

停下来并明确说明，列出你尝试过的方法，向用户请求：（a）能复现该问题的环境访问权限；（b）捕获的工件（HAR 文件、日志转储、core dump、带时间戳的屏幕录制）；或（c）添加临时生产插桩的权限。

在获得循环之前，**不得**继续提出假设。

#### 多组件系统

当系统包含多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：

在提出修复之前，先在**每个组件边界**添加诊断插桩：

- 记录进入组件的数据
- 记录离开组件的数据
- 验证环境/配置传播
- 检查各层状态

运行一次以收集证据，显示故障发生在**哪里**，然后分析证据以识别故障组件，再针对该特定组件进行调查。

#### 完成标准：能变红的紧致循环

阶段 1 在循环**紧致**且**能变红**时完成：你能指出**一个命令**（脚本路径、测试调用、curl），你**已经至少运行过一次**，且该命令：

- [ ] **能变红** —— 它驱动实际的 bug 代码路径，并断言**用户的确切症状**，因此在此 bug 上能变红，修复后变绿。
- [ ] **确定性** —— 每次运行结果一致（flaky bug：按上述要求，固定高复现率）。
- [ ] **快速** —— 秒级，而非分钟级。
- [ ] **可 agent 运行** —— 可无人值守运行。

如果你发现自己在拥有此命令之前就开始阅读代码构建理论，**停下来** —— 直接跳到假设正是本技能要防止的错误。

### 阶段 2：复现 + 最小化

运行循环。观察它变红，bug 出现。

确认：

- [ ] 循环产生**用户**描述的失败模式，而非附近碰巧发生的其他失败。
- [ ] 失败在多次运行中可复现（或对于非确定性 bug，具有足够高的复现率以供调试）。
- [ ] 你已捕获确切的症状。

**仔细阅读错误消息：** 不要跳过错误或警告。完整阅读堆栈跟踪。注意行号、文件路径、错误码。

**检查近期变更：** 什么变更可能导致此问题？Git diff、最近提交、新依赖、配置变更、环境差异。

#### 最小化

一旦变红，将复现缩小到**仍能变红的最小场景**。每次减少输入、调用方、配置、数据、步骤**一个**，并在每次减少后重新运行循环，只保留对失败起关键作用的部分。

最小化复现缩小了假设空间（可疑的变动部分更少），并可作为后续干净的回归测试。

当**每一个剩余元素都是关键**时完成，移除其中任何一个都会使循环变绿。

在完成复现**且**最小化之前，不得继续。

### 阶段 3：根因调查

#### 追踪数据流

当错误发生在调用栈深处时：

- 坏值来自哪里？
- 是什么用坏值调用了这段代码？
- 持续向上追踪，直到找到源头。
- 在源头修复，而非症状处。

#### 模式分析

1. **寻找工作示例：** 在同一个代码库中找到类似的正常工作代码。
2. **对照参考实现：** 如果正在实现某种模式，完整阅读参考实现。不要略读，逐行阅读。在应用之前完全理解该模式。
3. **识别差异：** 工作代码与损坏代码之间有何不同？列出所有差异，无论多小。不要假设“那不可能有关系”。
4. **理解依赖：** 该代码需要哪些其他组件？需要什么设置、配置、环境？它做出了哪些假设？

### 阶段 4：提出假设

在测试任何假设之前，生成 **3–5 个排好序的假设**。单假设生成会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：说明它作出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会使 bug 消失 / <改变 Z> 会使它更严重。”

如果你无法说明预测，则该假设只是一种感觉，放弃或将其锐化。

**在测试之前向用户展示排序列表。** 用户通常拥有领域知识，能立即重新排序（“我们刚刚部署了对 #3 的变更”），或者知道他们已经排除的假设。如果用户不在，不要阻塞，按你的排序继续。

### 阶段 5：插桩与测试

每个探测必须对应阶段 4 中的一个具体预测。**一次只改变一个变量。**

工具优先级：

1. **调试器 / REPL 检查**（如果环境支持）—— 一个断点胜过十行日志。
2. **定向日志** —— 在能区分假设的边界处添加。
3. 永远不要“记录所有内容再 grep”。

为每条调试日志添加**唯一前缀**，例如 `[DEBUG-a4f2]`。最终清理时只需一次 grep。

**性能分支。** 对于性能回归，日志通常是错误的。替代方案：建立基准测量（计时工具、`performance.now()`、性能分析器、查询计划），然后进行二分。先测量，后修复。

**最小化测试：** 做**尽可能小**的变更来检验假设。不要一次性修复多个问题。

- 测试通过？进入阶段 6。
- 测试失败？形成**新的**假设（回到阶段 4）。
- 如果 ≥ 3 个假设均失败：**停止并质疑架构**（参见下文“何时质疑架构”）。

### 阶段 6：修复 + 回归测试

**在修复之前先创建一个失败测试** —— 但前提是存在**正确的接缝**。

正确的接缝是指测试能在调用点按**真实 bug 模式**进行演练。如果唯一可用的接缝太浅，则回归测试会带来虚假信心。

如果存在正确的接缝：

1. 将最小化复现转换为该接缝处的失败测试。
2. 观察它失败。
3. 应用**单一修复** —— 解决根因，一次只做一个变更。不要“顺便”改进。不要捆绑重构。
4. 观察它通过。
5. 针对原始（未最小化）场景重新运行阶段 1 的反馈循环。

**如果不存在正确的接缝，这本身就是发现。** 记录下来：代码库架构阻止了对该 bug 的锁定。

**如果修复不奏效：** 停止，统计你已经尝试了多少次修复。如果 < 3，带着新信息回到阶段 3；如果 ≥ 3，质疑架构（见下文）。

### 阶段 7：清理 + 事后分析

在声明完成之前必须完成：

- [ ] 原始复现不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或记录接缝缺失的原因）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 该前缀）
- [ ] 临时原型已删除（或移至明确标记的调试位置）
- [ ] 在提交 / PR 消息中说明已确认的根因，以便下一位调试者学习

**然后问：什么本可以预防这个 bug？** 如果答案涉及架构变更（缺乏良好的测试接缝、调用方纠缠、隐藏耦合），则在修复之后提出该建议。

## 何时质疑架构

如果你已尝试 3 次以上修复，且每次都暴露出新的共享状态、耦合或不同位置的问题：

**表明架构问题的模式：**

- 每次修复都暴露出其他位置的新症状
- 修复需要“大规模重构”才能实施
- 你“纯粹靠惯性硬撑着”

**停下来与你的搭档讨论：**

- 这个模式从根本上合理吗？
- 我们是否应该重构架构，而不是继续修复症状？

这不是假设失败，这是错误的架构。

## 危险信号 —— 停止并遵循流程

如果你发现自己产生以下想法：

- “先快速修复，以后再调查”
- “就试着改 X 看看行不行”
- “问题很简单，不需要流程”
- “紧急情况，没时间走流程”
- “就这一次，先修了再调查”
- “确认修复有效后再写测试”
- “一次多个修复节省时间”
- “再试一次修复”（当已经试了 2 次以上）
- “我手动验证一下”（跳过测试）
- 在追踪数据流之前提出解决方案

**这些统统意味着：停止。回到阶段 1。**

## 常见辩解

| 借口 | 事实 |
|--------|---------|
| “问题简单，不需要流程” | 简单问题也有根因。对于简单 bug，流程执行很快。 |
| “紧急情况，没时间走流程” | 系统性调试比猜测-检查的反复折腾**更快**。 |
| “先试这个，再调查” | 第一次修复会定下基调。从一开始就做对。 |
| “确认修复有效后再写测试” | 未经测试的修复无法持久。先测试才能证明。 |
| “一次多个修复节省时间” | 无法隔离哪个有效。还会引入新 bug。 |
| “我看到问题了，让我修” | 看到症状 ≠ 理解根因。 |
| “再试一次修复”（在 2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，而非再次修复。 |

## 用户给出的你正在犯错的信号

注意这些转向提示：

- “那不是没发生吗？” —— 你在未经验证的情况下做了假设
- “它会向我们展示……吗？” —— 你本应收集证据
- “别猜了” —— 你在不理解的情况下提出修复
- “我们卡住了？”（语气沮丧）—— 你的方法不起作用

当你看到这些时：停止。回到阶段 1。

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 反馈回路** | 构建紧致、能变红的信号 | 一个能捕获 bug 的命令 |
| **2. 复现 + 最小化** | 确认 bug，缩小复现 | 保留最小关键输入 |
| **3. 根因** | 追踪数据流，模式分析 | 理解是什么和为什么 |
| **4. 假设** | 生成 3–5 个可证伪的预测 | 排序列表，与用户共享 |
| **5. 插桩与测试** | 一次探测一个变量 | 确认原因或新假设 |
| **6. 修复 + 回归测试** | 修复前先测试，仅一次变更 | bug 解决，回归通过 |
| **7. 清理 + 事后分析** | 移除插桩，记录文档 | 根因记录，预防措施注明 |

## 辅助技术

位于本技能的 `references/` 目录中：

- **`references/root-cause-tracing.md`** —— 沿调用栈向后追溯 bug 以找到原始触发点（包含 `references/find-polluter.sh`，一个测试污染二分脚本）
- **`references/defense-in-depth.md`** —— 找到根因后，在多层添加验证
- **`references/condition-based-waiting.md`** —— 将任意超时替换为条件轮询（包含 `references/condition-based-waiting-example.ts`）

## 当流程揭示“无根因”时

如果系统性调查揭示问题确实是环境性、时间依赖性或外部因素导致的：

1. 你已经完成了流程。
2. 记录你调查过的内容。
3. 实施适当处理（重试、超时、错误消息）。
4. 添加监控/日志以便未来调查。

**但：** 95% 的“无根因”案例都是调查不完整。
