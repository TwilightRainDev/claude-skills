# SKILL.md 语言与形态契约（skill-voice-contract）

改写技能 SKILL.md 时遵循的表达与形态规范。改写只动表达形式，不动技能机制。

**适用范围**：本契约约束**文风改写**，不豁免缺陷。遇到失效路径、指向不存在文件的引用、与磁盘实况矛盾的命令时，按缺陷单独修复，不得以「逐字保留」为由把它们一起保下来。

## 四项验收标准

| 标准 | 判据 |
|---|---|
| 结构清晰 | 标题层级规整，可跳读定位；可枚举内容用表格或编号列表，不用散文 |
| 自信 | 祈使句／陈述句下指令，无对冲词；例外写成「当 X 时 → Y」的可观察条件 |
| 无叙事 | 无来历、无过程故事、无元叙述、无第一人称反思；规则的一句因果保留 |
| 适合模型遵循 | 每步 = 动作 + 可观察完成判据；决策点写成条件 → 动作；命令与路径逐字可执行 |

## 硬性不变量

违者退回重做。

1. 文件路径与文件名不变：`<skills>\<Name>\SKILL.md`。
2. frontmatter `name` 一字不改，必须等于目录名。
3. `description` 保持「仅触发条件 + 第三人称」。原有触发关键词（症状、报错串、同义词、工具名、中文口语句式）一个都不能丢 —— Ask 路由与技能发现都依赖它们。仅在描述总结工作流时才改写，总长 ≤1024 字符。措辞规范见 SKILL.md「技能发现优化（SDO）」。
4. 一切可执行内容逐字保留：确切命令、参数、路径、脚本名、跨技能文件引用（如 `ReviewPr/references/review-protocol.md`）、代码块内标识符。
5. 只改 SKILL.md。`references/`、`scripts/`、`assets/` 下的文件一律不动。
6. 禁止 Emoji；行尾 LF；UTF-8 无 BOM。

## 灵魂保护条款

**只改表达形式，不改技能的灵魂。**

每个技能都有一处「机制内核」—— 它之所以起作用的那个判据、视角或框架。改写必须让它原样存活，即使它的表述看起来像散文。

判定方法：把这段话删掉，技能是否还教得会？教不会的就是内核，保留。

- 保留例：ThinkFirst 的「你先在心里形成想法再说出口」这一前提；HumanizerZh 的中文去 AI 味判据；TDD 的铁律与其对应反驳。
- 删除例：任何「我们当初为什么这么设计」的解释段、任何会话轶事。

禁止把技能改写成通用模板。某技能现有结构已服务于其机制时（如刻意极简的单文件引导）→ 保持该形态，只做去叙事与去对冲。

## 形态骨架

创建新技能所用的模板与 frontmatter 约束见 `references/skill-structure-template.md`；本节列出改写时必须满足的形态。

```markdown
# <技能名>

<一句话：这个技能做什么。陈述句，不写来历。>

## 何时使用
触发场景与症状；不适用情形写成“不使用：…”。

## <核心流程 / 分阶段小节>
编号步骤。每步 = 动作 + 可观察完成判据。
非显而易见的决策点写成：当 <可观察谓词> 时 → <动作>。

## 快速参考 / 常见错误 / 红旗信号
有真实内容才写，没有内容不要发明。
```

- **必填**：H1、一句话、`## 何时使用`、该技能的操作性小节。
- 骨架与 `references/skill-structure-template.md` 同构；H1 下的一句话即「概述」，不另设标题；选填小节按需取用，可合并。
- **H1 规范**：`# <技能名>`，技能名与目录名、frontmatter `name` 三者一致，可附加中文释义（如 `# Ask（技能路由）`）。缺 H1 的文件必须补上。
- **选填**：快速参考 / 常见错误 / 红旗信号 —— 有真实内容才写，没有内容不要发明。
- 已有等价小节（如 `## 铁律`、`## 三档投入`）可保留原名，不必强行套模板名。
- 已有合理的分阶段结构（阶段 0/1/2）保持不动，只做语言层清理。
- **标点**：中文正文内一律使用全角标点与弯引号 `“”`；代码、命令、路径、技能名保持原样。
- 大段代码、数据契约、输出模板的处置见 SKILL.md「代码块哲学」；指导形式的选取见 SKILL.md「指导形式必须与失败类型匹配」。

## 语言细则

### 删除 —— 无叙事

- **来历与动机**：「这个技能是为了…」「当初…」「在实践中我们发现…」
- **过程故事**：「先试了 X，行不通，改成 Y」；带日期的会话轶事
- **元叙述**：「本技能将…」「接下来…」「值得注意的是…」「需要强调的是…」「总而言之」
- **第一人称反思与自我贬低**
- **装饰**：ASCII 横幅、孤立的反引号伪代码围栏

### 改写 —— 自信

| 原表述 | 改为 |
|---|---|
| 你可以考虑执行 X | 执行 X |
| 建议使用 Y | 使用 Y |
| 如果可能的话… | 删除，或写成明确条件 |
| 视情况而定 | 当 <谓词> 时 → A；否则 → B |
| 尽量不要… | 不要…（或写出违反后的可观察后果） |
| 这只是一个粗略的… | 删除自我贬低，直接给判据 |

**对冲词清单**：可以、或许、也许、大概、建议、尽量、尝试、按理说、一般来说、视情况而定。

以下不算对冲，保留：

- 表达真实条件的「当…时」「若…则」「除非…」；
- 描述真实风险的「可能」（如「该命令可能丢弃未提交的改动」是陈述事实）。

### 因果 ≠ 叙事

一条规则存在的原因用**一句话**说明，帮助模型泛化；超过一句就是设计者说明，压缩成一句或删。

- 保留：「没有先看到失败测试，就无法确认测试测的是对的东西。」
- 压缩：整段论证 TDD 为何优于先写实现。

### 结构化

- 可枚举内容（选项、信号、命令、错误、判据）一律转表格或编号列表。
- 段落内不写「首先／其次／最后」的序数散文，改用编号列表。
- 一段超过 4 行且含多个要点 → 拆。

## 篇幅

- 硬约束：**不得新增原文没有的事实、规则、命令或示例**。
- 默认结果：叙事清理应让总行数下降。
- 例外：补齐必需骨架、散文转表格等结构性改动允许净增，增幅以改写前为基准 ≤10%。
- 不得为凑骨架而灌水，也不得为缩短而删掉操作性指令。
- 拿不准某句是否操作性 → 保留。
