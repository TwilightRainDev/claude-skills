# VerifyFirst（先验证）

始终先有证据，再有断言。**违反此规则的字面意思，就是违反此规则的精神。**

## 何时使用

**始终在以下情况之前：**

- 任何形式的成功/完成声明
- 任何满意表达
- 任何关于工作状态的正面陈述
- 提交、创建 PR、完成任务
- 进入下一个任务
- 委托给智能体

**规则适用于：**

- 精确短语
- 释义和同义词
- 成功的暗示
- 任何暗示完成/正确的交流

## 铁律

> **没有新鲜验证证据，就没有完成声明**

如果你没有在此条消息中运行过验证命令，就不能声称它通过。

## 关卡函数

在声称任何状态或表达满意之前：

1. **识别**：什么命令能证明此声明？
2. **运行**：执行完整的命令（新鲜的、完整的）
3. **读取**：完整输出，检查退出码，统计失败数
4. **验证**：输出是否确认了该声明？
   - 否 → 用证据说明实际状态
   - 是 → 用证据说明声明
5. **只有在此之后**：才能做出声明

跳过任何一步 = 撒谎，而非验证。

## 常见失败

| 声明 | 需要 | 不充分 |
|---|---|---|
| 测试通过 | 测试命令输出：0 失败 | 之前的运行、“应该能通过” |
| Linter 干净 | Linter 输出：0 错误 | 部分检查、外推 |
| 构建成功 | 构建命令：退出码 0 | Linter 通过、日志看起来不错 |
| 缺陷已修复 | 测试原始症状：通过 | 代码改了、假设已修复 |
| 回归测试有效 | 红-绿循环已验证 | 测试通过一次 |
| 智能体已完成 | VCS diff 显示变更 | 智能体报告“成功” |
| 需求已满足 | 逐行检查清单 | 测试通过 |

## 危险信号 —— 停止

- 使用“应该”、“可能”、“似乎”
- 在验证之前就表达满意（“太好了！”、“完美！”、“搞定！”等）
- 即将提交/推送/创建 PR 而未验证
- 信任智能体的成功报告
- 依赖部分验证
- 心想“就这一次”
- 累了，想结束工作
- **任何暗示成功却未运行验证的措辞**

## 防止合理化

| 借口 | 现实 |
|---|---|
| “现在应该能工作了” | 运行验证 |
| “我有信心” | 信心 ≠ 证据 |
| “就这一次” | 没有例外 |
| “Linter 通过了” | Linter ≠ 编译器 |
| “智能体说成功了” | 独立验证 |
| “我累了” | 疲劳不是借口 |
| “部分检查就够了” | 部分证明不了任何事 |
| “用了不同的话，所以规则不适用” | 重精神甚于字面 |

## 关键模式

**测试：**

```
[OK] [运行测试命令] [看到：34/34 通过] “所有测试通过”
[FAIL] “现在应该能通过” / “看起来正确”
```

**回归测试（TDD 红-绿）：**

```
[OK] 编写 → 运行（通过）→ 还原修复 → 运行（必须失败）→ 恢复 → 运行（通过）
[FAIL] “我已经写了回归测试”（没有红-绿验证）
```

**构建：**

```
[OK] [运行构建] [看到：退出码 0] “构建通过”
[FAIL] “Linter 通过了”（Linter 不检查编译）
```

**需求：**

```
[OK] 重新阅读计划 → 创建检查清单 → 逐项验证 → 报告缺口或完成
[FAIL] “测试通过了，阶段完成”
```

**委托智能体：**

```
[OK] 智能体报告成功 → 检查 VCS diff → 验证变更 → 报告实际状态
[FAIL] 信任智能体报告
```
