# ADR 格式

ADR 存放在 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

仅在需要第一个 ADR 时，才惰性地创建 `docs/adr/` 目录。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么，我们决定了什么，以及为什么。}
```

就这样。一个 ADR 可以是一个段落。其价值在于记录*做了*一个决定以及*为什么* —— 而不是填写各种小节。

## 可选部分

仅当这些部分能带来真正价值时才包含它们。大多数 ADR 不需要它们。

- **Status** 前置元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）—— 当决策被重新审视时很有用
- **Considered Options** —— 仅当被否决的替代方案值得记住时
- **Consequences** —— 仅当需要指出非显而易见的后续影响时

## 编号

扫描 `docs/adr/` 获取现有最大编号，并递增一。

## 何时提供 ADR

以下三点必须全部满足：

1. **难以逆转** —— 事后改变主意的成本是有意义的
2. **脱离上下文会令人惊讶** —— 未来的读者看到代码时会想“他们到底为什么这样做？”
3. **是真实权衡的结果** —— 存在真正的替代方案，并且你出于特定原因选择了其中一个

如果一个决定容易逆转，就跳过 —— 反正你会把它逆转回去。如果不会令人惊讶，没人会想知道为什么。如果没有真正的替代方案，除了“我们做了显而易见的事”之外，没有什么需要记录的。

### 什么符合条件

- **架构形态。** “我们采用 monorepo。”“写模型是事件溯源，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。”
- **带有锁定效应的技术选择。** 数据库、消息总线、认证提供商、部署目标。不是每个库 —— 只是那些替换起来需要花一个季度的。
- **边界和范围决策。** “客户数据归属于 Customer 上下文；其他上下文仅通过 ID 引用它。”明确的不做什么，和做什么一样有价值。
- **对显而易见路径的刻意偏离。** “我们使用手动 SQL 而不是 ORM，因为 X。”任何有合理判断力的读者会假设相反情况的地方。这些能阻止下一位工程师去“修正”那些本来就是刻意为之的东西。
- **代码中不可见的约束。** “由于合规要求，我们不能使用 AWS。”“由于合作伙伴 API 合约，响应时间必须在 200ms 以内。”
- **当否决理由非显而易见时，记录被否决的替代方案。** 如果你考虑了 GraphQL 并因为微妙原因选择了 REST，记录下来 —— 否则六个月后又会有人建议 GraphQL。
