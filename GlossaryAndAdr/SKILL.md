# GlossaryAndAdr（术语表与 ADR）

在设计过程中主动构建并完善项目的领域模型：挑战术语、发明边缘场景，并在术语与决策明确的瞬间记录下来。

## 何时使用

- 你正在改变领域模型：确定术语、界定概念边界、做出架构决策。
- 用户使用的术语与现有语言冲突，或用词模糊、过载。

不使用：仅为查阅词汇而阅读 `CONTEXT.md` —— 那是任何技能都可以做的一行式习惯。本技能适用于改变模型时，而不仅仅是消费它。

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录下存在 `CONTEXT-MAP.md`，则该仓库有多个上下文。该映射文件指向每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定的决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性创建文件 —— 有内容要写入时才创建。`CONTEXT.md` 不存在时 → 在第一个术语确定时创建。`docs/adr/` 不存在时 → 在需要第一个 ADR 时创建。

## 会话期间

| 挑战 | 触发条件 → 动作 |
|---|---|
| 对照术语表进行挑战 | 用户使用的术语与 `CONTEXT.md` 中现有语言冲突 → 立即指出来。“你的术语表将 ‘cancellation’ 定义为 X，但你似乎指的是 Y —— 到底是哪个？” |
| 优化模糊语言 | 用户使用模糊或过载的术语 → 提出一个精确的规范术语。“你说的 ‘account’ —— 是指 Customer 还是 User？它们是不同的东西。” |
| 讨论具体场景 | 讨论领域关系 → 用具体场景对其进行压力测试。编造探查边缘情况的场景，迫使用户精准界定概念之间的边界。 |
| 与代码交叉验证 | 用户说明某个功能的工作方式 → 检查代码是否一致。发现矛盾时指出来：“你的代码取消了整个 Order，但你刚才说部分取消是可能的 —— 哪个是正确的？” |

### 内联更新 CONTEXT.md

当一个术语确定后，立即在 `CONTEXT.md` 中更新。不要批量处理 —— 发生时就捕捉。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应完全不含实现细节。不要把 `CONTEXT.md` 当作规格说明、草稿纸或实现决策的存储库。它只是一个术语表，仅此而已。

### 谨慎提供 ADR

仅在以下三个条件都满足时才提供创建 ADR：

1. **难以逆转** —— 事后改变主意的成本是有意义的
2. **脱离上下文会令人惊讶** —— 未来的读者会想“他们为什么这样做？”
3. **是真实权衡的结果** —— 存在真正的替代方案，并且你出于特定原因选择了其中一个

如果三条中任意一条不满足，跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
