# HumanizerZh（中文去 AI 味）

让中文读起来像人写的，附带标点全半角归一化与隐形字符清理。

## 何时使用

- 中文文本读起来像 AI 写的，需要改写。
- 需要做标点归一化：重复标点、全半角混用、隐形字符、省略号风格。

不使用：改内容事实、翻译、摘要。

## 概述

分两层，**顺序不能反**：

| 层 | 手段 | 管什么 |
|---|---|---|
| **机械层** | TextTool CLI 的 `replace` | 重复标点、全半角混用、隐形字符、省略号风格 —— 确定性的字符问题 |
| **判断层** | `texttool lint` 报位 + 你判断改写 | 对举句式、序数词骨架、结尾升华、套话词 —— 句式与腔调问题 |

先机械后判断：标点噪音清掉之后，剩下的才是真正要动笔的地方；反过来做会把字符问题误诊成风格问题，改出一堆不必要的句子。

机械层只做等价的字符级替换，不改变语义。

## 机械层：texttool replace

`replace` 命令按替换方案做确定性归一化。方案 `去AI味标点归一` 覆盖四类：

- **隐形字符清除** —— 零宽空格（U+200B）、BOM（U+FEFF）、软连字符（U+00AD）、不换行空格（U+00A0，转普通空格）。**零宽非连接符（U+200C）与零宽连接符（U+200D）不在其列**：方案不动这两个，但 `P7` 会报——跑完方案还剩这两处命中属预期，不是没跑成功
- **省略号统一** —— 点号串转标准省略号：`...`、`....`、`......` 与单个 `…` 都转 `……`；已是 `……` 的原样保留；`..`（两点）没有对应规则，不动
- **重复标点折叠** —— `。。`→`。`、`！！`→`！`、`，，`→`，`，含 `。，`、`，？` 这类混乱组合。**`。。。` 走的是这一条，不是省略号那条**：一遍只收一格（`。。。`→`。。`），要跑第二遍才到 `。`，**永远不会变成 `……`**
- **全角转半角** —— 全角字母与数字（`ＡＢＣ`→`ABC`、`１２３`→`123`）

### 三个必须知道的坑

**一、它从不覆盖原文件。** 产物固定写成同目录下的 `<原名>_Processed.<扩展名>`，原文件保持不动。别指望“就地改完”——要把产物接着处理（重命名、或作为下一步输入）。

**二、产物是 UTF-8 带 BOM。** 这与本机“LF、无 BOM”的约定冲突；直接把产物当成品交出去会把 BOM 带进下游。需要剥离时用 `python -c "import pathlib;p=pathlib.Path(r'<文件>');p.write_bytes(p.read_bytes().lstrip(b'\xef\xbb\xbf'))"` 或 `sed -i '1s/^\xEF\xBB\xBF//' <文件>`。源文件的编码会被自动识别（BOM → UTF-8 校验 → GBK 回退），**识别出来是 GBK 时产物会被转成 UTF-8**，这是有损上下文的变化，交付前确认对方能接受。

**三、方案必须装在 CLI 可执行文件所在目录。** 规则文件从 `AppContext.BaseDirectory` 读，不是当前工作目录、也不是技能目录。`去AI味标点归一` **不是内置方案**（内置 9 个方案里没有它），必须用技能自带脚本装过去：`python <skill>/scripts/install_scheme.py`。脚本把自带方案并入目标目录已有的 `replace_schemes.json`（同名覆盖、其余保留，不破坏你已有的方案）。首次使用前若 CLI 尚未构建，先建一次：`cd E:\work_zone\Code\TextTool && dotnet build -c Release`。

`SuggestScheme` 可能指向的另外三个方案（`重复矛盾标点整理`、`特殊符号清除`、`引号括号统一`）都是内置的，不用装。

### 命令

```
<CLI> replace <文件...> --scheme 去AI味标点归一
```

## 判断层：texttool lint

只报位置、不改写。输出 JSON 契约，直接读 `Hits` 逐条处理。

```
<CLI> lint <文件> --json
<CLI> lint - --json              # 从 stdin 读
<CLI> lint <文件> --only S1,L1
<CLI> lint <文件> --min-severity warn
```

退出码：`0` 无命中、`1` 有命中、`2` 用法或读取错误。能直接当 CI 关卡用。

省略 `--json` 时输出人读报告：`[命中] <Id> <标题>（N 处）` 逐行给出 `第 L 行 第 C 列  片段  <- 触发原因`，末尾 `[统计]` 列 `Notes`、`[NOTE]` 给总字数与命中数；无命中时首行是 `[OK] 未发现可疑特征`。

### JSON 契约

```
{ "Version": 1,
  "Reports": [ { "File", "Chars",
                 "Hits":  [ { Id, Group, Title, Severity, Line, Col,
                              Length, Match, Snippet, Detail,
                              Hint, SuggestScheme } ],
                 "Notes": [ { Id, Text } ] } ] }
```

字段全 PascalCase。`File` 在 stdin 模式下是 `(stdin)`。行列从 1 开始。

### 三组规则码

命中分三组：`P` 机械层（标点与字符）、`L` 词汇层、`S` 句式层。

- `P` 组带 `SuggestScheme`，告诉你要跑哪条方案去修（`L`/`S` 组该字段为 null，属于判断层，没有现成方案）。
- `Notes` 是统计观察（段落/句长变异系数等），**不计入退出码**。
- 共 26 条：数据规则 19 条（`P1/P2/P3/P6/P7/P8`、`L1`–`L7`、`S1`–`S6`）+ 算法规则 7 条（`P4`/`P5` 进 `Hits`，`C1`–`C5` 进 `Notes`）。

### `--only` 与退出码的实际行为

- `--only` **同时过滤 `Hits` 与 `Notes`**（按 Id、大小写不敏感）——实测 `--only S1` 不带出任何统计项，`--only C1` 只报 C1 的统计项。
- 退出码只看**过滤后**的 `Hits`。C 组只进 `Notes`，所以 `--only C5` 即使报出了 C5 统计项，退出码仍是 **0**。
- `--min-severity warn` 同理作用在 `Hits` 上（`info` 级如 `P4`/`P6`/`P8` 被滤掉），是关卡松紧的旋钮。
- `--only` 传未知 Id **报错退 2**，不静默忽略——拼错的规则名不会表现为“跑过了没问题”。

## 判断层改写要点

报出来的命中是**候选**，不是判决。真实语境里对举句式和套话词都可能是恰当的，改之前先问“这里换成人的说法会怎么说”。

- 倾向于保留：具体的名词、数字、专有名词、人物原话。
- 倾向于改写：抽象名词堆叠、无信息量的过渡句、每段结尾的拔高、为了对称而凑的排比。

段落长短是最容易见效的一处：把均一的段落拆成长短交错，比逐句润色更快消除机器感。

## 三步流程

1. `<CLI> lint <文件> --json` —— 读 `Hits` 与 `Notes`，先看清问题分布。
2. 对带 `SuggestScheme` 的 `P` 组命中，跑它指向的方案做机械修复，产出 `*_Processed.*`。
3. 剩下的 `L`/`S` 组自己判断改写，再跑一次 `lint` 复核。

机械修复后**必须重跑 lint**：方案的改动是字面的，可能带出新的命中（见「已知边界」）。

## 常见错误

| 错误 | 纠正 |
|---|---|
| 跑完机械层就交付 | 标点归一化去不掉对举句式和结尾升华，AI 味的大头在句式不在标点。机械层只是把噪音清掉，好让判断层看清剩下的问题 |
| 以为 `replace` 会就地改 | 它写 `*_Processed.*`，从不覆盖。找不到改动痕迹时先看目录里是不是多了个 `_Processed` 文件 |
| 忽略 BOM | 产物带 BOM 是实测行为。直接把它当成品交付，会把 BOM 带进下游工具链 |
| 把 `lint` 的命中当成必须全改 | 它只报位置。套话词在引语里、对举句式在真实对比里，都是正常的 |
| 忘了方案没装 | 报 `错误：未找到方案：去AI味标点归一` 时，先跑 `install_scheme.py`。`去AI味标点归一` 不是内置的 |
| 看到 `[成功]` 显示成乱码以为失败了 | `replace` 的成功提示走控制台码页（GBK），在 UTF-8 终端里会花屏；`lint` 的输出才是标准 UTF-8。认退出码 0 即可 |
| 以为 `--only` 只过滤 `Hits` | 它按 Id 同时过滤 `Hits` 与 `Notes`；退出码仍只看 `Hits` |
| 照旧报告念 `S5` | 旧 `S5` 是套话词（现 `L1`），新 `S5` 是系动词回避。同名不同义 |

## 已知边界

- 自带方案含一条 **U+E000（私用区字符）→ `……`** 的规则。文本若合法使用私用区（图标字体、自定义编码），这条会破坏内容——遇到这类文本先从方案里删掉该条。
- 方案的替换是**字面**匹配，不是正则；靠叠加多条规则覆盖变体（如 `。，`、`，。` 分别列）。
- `replace` 不做语义判断，也不管句式；它只保证字符层面的确定性。
- **方案之间会互相打架。** 实测 `引号括号统一` 把全角括号转成半角（`（括号）`→`(括号)`）、把 `【】`转成`「」`，而半角括号夹在中文里正好触发 `P3`——跑完它的文件 `P3` 命中数反而上升。方案是字面替换，不理解它自己制造了什么，所以**每跑一条方案就重跑一次 `lint`**。
- **`SuggestScheme` 只表示“这条方案管这类问题”，不代表跑完就修好了。** 典型例子：`P2`（省略号风格）指向 `去AI味标点归一`，而该方案只把 ASCII 点号串转成 `……`；文本里的 `。。。` 根本不走省略号那条规则，一遍只到 `。。`、两遍才到 `。`，跑多少遍都变不成 `……`。跑完方案要再 `lint` 一次，确认那条命中真的消失了。
- 段落口径 = **非空行**。Markdown 软换行会被拆成多段，是已知简化（与旧 `tone_lint.py` 一致）。
- **隐形字符在两种输出里都已转义**：人读模式与 `--json` 都把 `P7` 的命中渲染成 `\u200b` 这类转义写法（终端根本显示不出来）；JSON 解析方（`JSON.parse` 等）会把它解回原字符，语义不变，因此别拿 `Match` 的长度去数原文。
- `C` 组是统计观察，不是命中。变异系数低是 AI 文本的强信号——人写的段落长短天然参差，但别拿它当硬指标。

## 红旗信号

出现以下念头时停下来：

- “标点跑一遍就干净了” → 骨架还在，回判断层
- “产物改个名就当结果” → BOM 还在文件里
- “顺手覆盖原文件省事” → CLI 不支持，也不该支持
- “lint 报 20 处，全改” → 先逐条看语境，命中是候选不是判决
- “方案没装，我直接改技能里的 JSON” → 改错地方了，跑 `install_scheme.py`
- “方案跑完了，不用再看” → 方案会引入新命中，重跑 `lint`
