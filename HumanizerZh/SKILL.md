# HumanizerZh

## 概述

让中文读起来像人写的。分两层，**顺序不能反**：

| 层 | 手段 | 管什么 |
|---|---|---|
| **机械层** | TextTool CLI 的标点替换 | 重复标点、全半角混用、隐形字符、省略号风格 —— 确定性的字符问题 |
| **判断层** | `tone_lint.py` 报位 + 你判断改写 | 对举句式、序数词骨架、结尾升华、套话词 —— 句式与腔调问题 |

先机械后判断：标点噪音清掉之后，剩下的才是真正要动笔的地方；反过来做，容易把字符问题误诊成风格问题，改出一堆不必要的句子。

本技能不改内容事实、不做翻译和摘要。机械层只做等价的字符级替换，不改变语义。

## 机械层：TextTool CLI

`replace` 命令按替换方案做确定性归一化。自带方案 `去AI味标点归一` 覆盖四类：

- **隐形字符清除** —— 零宽空格/连接符、BOM、软连字符、不换行空格（空格转普通空格）
- **省略号统一** —— `...`、`......`、`。。。` 一律转 `……`
- **重复标点折叠** —— `。。`→`。`、`！！`→`！`、`，，`→`，`，含 `。，`、`，？` 这类混乱组合
- **全角转半角** —— 全角字母与数字（`ＡＢＣ`→`ABC`、`１２３`→`123`）

### 三个必须知道的坑

**一、它从不覆盖原文件。** 产物固定写成同目录下的 `<原名>_Processed.<扩展名>`，原文件保持不动。这是刻意的设计——所以别指望"就地改完"，要把产物接着处理（重命名、或作为下一步输入）。

**二、产物是 UTF-8 带 BOM。** 这与本机"LF、无 BOM"的约定冲突；直接把产物当成品交出去会把 BOM 带进下游。需要剥离时用 `python -c "import pathlib;p=pathlib.Path(r'<文件>');p.write_bytes(p.read_bytes().lstrip(b'\xef\xbb\xbf'))"` 或 `sed -i '1s/^\xEF\xBB\xBF//' <文件>`。源文件的编码会被自动识别（BOM → UTF-8 校验 → GBK 回退），**识别出来是 GBK 时产物会被转成 UTF-8**，这是有损上下文的变化，交付前确认对方能接受。

**三、方案必须装在 CLI 可执行文件所在目录。** 规则文件从 `AppContext.BaseDirectory` 读，不是当前工作目录、也不是技能目录。所以自带的方案要先"安装"过去：

```
python <skill>/scripts/install_scheme.py
```

脚本会把自带方案并入目标目录已有的 `replace_schemes.json`（同名覆盖、其余保留，不破坏你已有的方案）。首次使用前若 CLI 尚未构建，先建一次：

```
cd E:\work_zone\Code\TextTool && dotnet build -c Release
```

## 判断层：tone_lint.py

只报位置、不改写。纯标准库。

```
python <skill>/scripts/tone_lint.py <文件>          # 人读的报告
python <skill>/scripts/tone_lint.py <文件> --json   # 结构化
python <skill>/scripts/tone_lint.py -               # 从 stdin 读
python <skill>/scripts/tone_lint.py <文件> --only S1,S3
```

退出码：`0` 无命中、`1` 有命中、`2` 用法或读取错误。所以它能直接当 CI 关卡用。

它查两类特征：

- **机械类**（`P1`–`P7`）：重复标点、省略号风格混用、全半角混用、引号/括号风格不统一、破折号写法、波浪号、隐形字符
- **句式类**（`S1`–`S5`）：对举句式（`不是A而是B` 一族）、段内序数词、结尾升华、定语堆叠（短距离三个「的」）、套话词

外加若干统计项（不占命中数）：省略号/引号/括号风格混用、叹号密度、段落长度变异系数、句长分布变异系数、段首两字重复。**变异系数低是 AI 文本的强信号**——人写的段落长短天然参差。

## 判断层改写要点

报出来的命中是**候选**，不是判决。真实语境里对举句式和套话词都可能是恰当的，改之前先问"这里换成人的说法会怎么说"。

倾向于保留：具体的名词、数字、专有名词、人物原话。倾向于改写：抽象名词堆叠、无信息量的过渡句、每段结尾的拔高、为了对称而凑的排比。

段落长短是最容易见效的一处：把均一的段落拆成长短交错，比逐句润色更快消除机器感。

## 常见错误

**跑完机械层就交付** —— 标点归一化去不掉对举句式和结尾升华，AI 味的大头在句式不在标点。机械层只是把噪音清掉，好让判断层看清剩下的问题。

**以为 `replace` 会就地改** —— 它写 `*_Processed.*`，从不覆盖。找不到改动痕迹时先看目录里是不是多了个 `_Processed` 文件。

**忽略 BOM** —— 产物带 BOM 是实测行为。直接把它当成品交付，会把 BOM 带进下游工具链。

**把 `tone_lint` 的命中当成必须全改** —— 它只报位置。套话词在引语里、对举句式在真实对比里，都是正常的。

**忘了方案没装** —— 报 `没有可用的替换规则` 时，先跑 `install_scheme.py`，别去改技能里的方案文件。

## 已知边界

- 自带方案含一条 **U+E000（私用区字符）→ `……`** 的规则。文本若合法使用私用区（图标字体、自定义编码），这条会破坏内容——遇到这类文本先从方案里删掉该条。
- 方案的替换是**字面**匹配，不是正则；靠叠加多条规则覆盖变体（如 `。，`、`，。` 分别列）。
- `replace` 不做语义判断，也不管句式；它只保证字符层面的确定性。

## 红旗信号

出现以下念头时停下来：

- "标点跑一遍就干净了" → 骨架还在，回判断层
- "产物改个名就当结果" → BOM 还在文件里
- "顺手覆盖原文件省事" → CLI 不支持，也不该支持
- "tone_lint 报 20 处，全改" → 先逐条看语境，命中是候选不是判决
- "方案没装，我直接改技能里的 JSON" → 改错地方了，跑 `install_scheme.py`
