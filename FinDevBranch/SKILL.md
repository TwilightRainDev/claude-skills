# FinDevBranch（完成开发分支）

实现完成、测试全过、合并之前收尾分支。**核心原则：验证测试 → 检测环境 → 呈现选项 → 执行选择 → 清理。**

开始时报出：“我正在使用 FinDevBranch 技能来完成这项工作。”

## 第 1 步：验证测试

运行项目的完整测试套件（`npm test` / `cargo test` / `pytest` / `go test ./...`）。

**测试失败** → 报告失败并停止，菜单要等到测试全部通过后才出现：

```
测试失败（<N> 个失败）。完成前必须修复：

[显示失败信息]
```

**测试通过** → 继续到第 2 步。

## 第 2 步：检测环境

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# 现在捕获，仍在工作区内部 —— 第 5 步在清理（第 6 步）之前会切换目录，
# 但清理需要这个值
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

环境决定显示哪个菜单以及如何清理：

| 状态 | 菜单 | 清理方式 |
|------|------|----------|
| `GIT_DIR == GIT_COMMON`（普通仓库） | 标准 3 个选项 | 无需清理工作树 |
| `GIT_DIR != GIT_COMMON`，命名分支 | 标准 3 个选项 | 基于来源清理（见第 6 步） |
| `GIT_DIR != GIT_COMMON`，分离 HEAD | 精简 2 个选项（无合并） | 外部管理 —— 保留不动 |

## 第 3 步：确定基础分支

基础分支是这项工作所分出的分支——通常在计划、对话或分支的上游中会有说明。尚不清楚时询问：“这个分支从 <你的最佳猜测> 分出 —— 对吗？”

合并之前确认：合并到错误的基础分支，撤销成本很高。

## 第 4 步：呈现选项

**普通仓库和命名分支工作树——呈现以下恰好 3 个选项：**

```
实现完成。你想做什么？

1. 合并回 <base-branch>（本地）
2. 推送并创建 Pull Request
3. 保持分支现状（我稍后处理）

选择哪个选项？
```

**分离 HEAD——呈现以下恰好 2 个选项：**

```
实现完成。你处于分离 HEAD（外部管理工作区）。

1. 作为新分支推送并创建 Pull Request
2. 保持现状（我稍后处理）

选择哪个选项？
```

完全按上述方式呈现菜单——简洁，且每个选项均来自上面的列表。只有在你的合作伙伴明确要求时，才丢弃工作（见“如果你的合作伙伴要求丢弃工作”）。等待他们的回答；集成决策由他们做出。

## 第 5 步：执行选择

### 选项 1：本地合并

```bash
# 为安全切换目录，获取主仓库根目录
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# 先合并 —— 在移除任何内容之前确认成功
git checkout <base-branch>
git pull
git merge <feature-branch>

# 在合并结果上验证测试
<test command>
```

合并后的测试失败 → 停止，保持工作树和分支不动，进行调查——没有推送任何内容，因此合并是本地的且可恢复。

合并结果通过测试后 → 清理工作树（第 6 步），然后删除分支：

```bash
git branch -d <feature-branch>
```

### 选项 2：推送并创建 PR

```bash
git push -u origin <feature-branch>
# 对于分离 HEAD，在远程上命名新分支：
# git push origin HEAD:refs/heads/<new-branch>
```

然后针对 <base-branch> 使用托管平台工具创建拉取/合并请求——有 CLI 则使用 CLI，否则使用大部分托管平台在推送时打印的创建 URL——遵循仓库的 PR 模板和惯例（如果有），并向你的合作伙伴报告 URL。

保留工作树——你的合作伙伴会在那里根据 PR 反馈进行迭代。

### 选项 3：保持现状

报告：“保留分支 <name>。工作树保留在 <path>。”

### 如果你的合作伙伴要求丢弃工作

此路径仅作为对明确要求放弃工作的响应而存在。先确认：

```
这将永久删除：
- 分支 <name>
- 所有提交：<commit-list>
- 位于 <path> 的工作树

输入 'discard' 确认。
```

等待这个确切的确认。收到后：

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

然后清理工作树（第 6 步）并强制删除分支：

```bash
git branch -D <feature-branch>
```

## 第 6 步：清理工作区

**适用于选项 1 和已确认的丢弃操作。** 选项 2 和 3 始终保留工作树。两个调用方都已将目录切换到主仓库根目录——工作树移除必须从工作树外部运行——并使用第 2 步中在目录切换之前捕获的 `GIT_DIR`/`GIT_COMMON`/`WORKTREE_PATH` 值。

**`GIT_DIR == GIT_COMMON`** → 普通仓库，没有工作树需要清理。完成。

**`WORKTREE_PATH` 位于 `.worktrees/` 或 `worktrees/` 下** → 创建了此工作树，我们拥有清理权：

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # 自愈：清理任何过时的注册信息
```

**其他情况** → 主机环境拥有此工作区，保留不动。如果你的平台提供了工作区退出工具，则使用它。

## 快速参考

| 选项 | 合并 | 推送 | 保留工作树 | 清理分支 |
|--------|------|------|-----------|----------|
| 1. 本地合并 | 是 | - | - | 是 |
| 2. 创建 PR | - | 是 | 是 | - |
| 3. 保持现状 | - | - | 是 | - |
| 丢弃（仅明确请求） | - | - | - | 是（强制） |

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| “这轮会话中测试之前通过了” | 在你即将集成的树上运行测试套件。一次绿色运行只能证明它运行过的那棵树。 |
| “他们显然想合并” | 集成是你合作伙伴的决定。呈现菜单并等待。 |
| “他们似乎已经完成了这个功能 —— 我主动提出丢弃它” | 菜单已经完整。丢弃只在你合作伙伴明确说出要求时才发生。 |
| “‘好，删掉’算作确认” | 只有键入的单词 `discard` 才授权删除。 |
| “PR 已经建了，所以工作树现在多余了” | PR 反馈会在那个工作树中修复。在代码合入之前它都保留。 |
| “这个其他工作树看起来过时了 —— 我也清理掉” | 只清理 `.worktrees/` 或 `worktrees/` 下的工作树。其他一切属于主机。 |
| “合并结果失败可能是偶发的” | 合并结果失败会停止一切。分支和工作树保持原样，由你调查。 |
| “基础分支显然是 main” | 确认分叉点或询问。合并到错误的基础分支撤销成本很高。 |
| “推送被拒绝 —— 强制推送可以修复” | 推送被拒绝意味着远程已移动。调查；强制推送仅在合作伙伴明确要求时进行。 |
