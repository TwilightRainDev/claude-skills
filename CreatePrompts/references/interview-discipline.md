# 面试式追问纪律（interview-discipline）

三种技能共用的追问纪律：**CreatePrompts**（阶段 1 刨根问底）、**WriteIssue**（第 2 步六要点简报）、**ProbeIntent**（对话纪律）。产物不同（prompt / issue / 设计），纪律同源。权威宿主为 `CreatePrompts`。

## 核心纪律（四条）

### 1. 单问题推进

- 每条消息只问一个问题。多部分话题拆成连续的问题，一次问多个会令人困惑。
- 优先使用选择题；选项空间未知时用开放式问题。
- 回答是下一步提问的唯一输入——不要走僵化脚本。

### 2. 先探索，再询问

如果代码库、文档或仓库能回答某个问题，先去探索，而不是询问用户。
"我需要更多上下文"不是跳过纪律的理由——纪律检查在澄清问题之前。

### 3. 缺项占位，不编造

每个信息槽位只有三种状态：**用户提供的值 / 明确的占位符 / 用户拒绝提供**。没有第四种。

| 技能 | 占位符 | 语义 |
|---|---|---|
| CreatePrompts | `[未指定]` | 维度未澄清或用户说没想过 |
| WriteIssue | `[待补充]` | 槽位缺用户信息 |
| ProbeIntent | 明确标记"稍后决定" | 决策点暂缓 |

- 绝不用自己的知识、常识或领域经验填补空白。
- 用户说"没想过"/"不清楚"/拒绝提供 → 接受，标占位符，继续。
- 从格式或上下文推断出的内容必须标注"推断/推测"，不得写成事实。

### 4. 快照确认后再产出

- 追问完成后，把收集到的信息整理成结构化快照（各维度逐项列出）。
- 呈现快照，请用户确认（是/否）。
- 否 → 问清要改哪部分，修订后重新呈现。是 → 才进入产出阶段（生成 prompt / 起草 issue / 呈现设计）。
- 未确认的快照不得作为产出输入。

## 各技能的应用差异

| 维度 | CreatePrompts | WriteIssue | ProbeIntent |
|---|---|---|---|
| 追问维度 | 六维（目标/受众/场景/流程/约束/成功标准） | 六槽（目标/环境/报错原文/已做功课/复现/实际vs预期） | 沿设计树分支走访 |
| 目的 | 挖掘提示词需求 | 收集 issue 证据 | 达成设计共识 |
| 产出前关卡 | 需求快照确认 | 自查清单（不编造逐项过） | 用户批准设计/共识总结 |
| 特有红线 | 只提问不评判不评估 | 发出去的每个字可溯源 | 没有共识不行动 |

## 快速参考

| 你的直觉 | 正确做法 |
|---|---|
| "一次把问题问完省时间" | 单问题推进，逐轮消化 |
| "这个明显缺信息，我补上" | 问用户，或标占位符 |
| "快照有点长，直接开始吧" | 快照确认是关卡，不可跳过 |
| "用户说过 X，所以 Y 也成立" | 追问验证，表面提及不等于深层清晰 |
| "先产出，缺的以后再问" | 缺项占位或先问，产出不允许带未确认假设 |
