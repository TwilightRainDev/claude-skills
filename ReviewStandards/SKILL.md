# ReviewStandards

从 `HEAD` 与用户提供的固定点之间的差异做双轴评审，两个轴作为**并行子智能体**运行、互不污染上下文，随后聚合两者的发现：

- **标准（Standards）** —— 代码是否符合此仓库文档化的编码规范？
- **规范（Spec）** —— 代码是否忠实地实现了原始问题/PRD/规格说明？

问题跟踪器信息：被评审仓库若有 `docs/agents/issue-tracker.md`，从中获取问题编号与关联方式；没有就向用户询问原始需求或 PRD，不要假定它存在。

## 何时使用

- 合并前需要同时评编码规范符合度与需求/PRD 符合度。
- 需要两个轴各自独立成报告、互不掩盖时。

## 流程

### 1. 固定固定点

按 `ReviewPr/references/review-protocol.md` 的“固定点模式”执行：用户所说的任何内容就是固定点 —— 一个提交 SHA、分支名称、标签、`main`、`HEAD~5` 等；用户未指定 → 询问。捕获一次差异命令（三个点，比较 merge-base）并记录提交列表；确认固定点能解析（`git rev-parse <fixed-point>`）且差异非空。无效引用或空差异在这里失败 —— 不在两个并行子智能体内部。

### 2. 识别规范来源

按以下顺序查找原始规范：

1. 提交消息中的问题引用（`#123`、`Closes #45`、GitLab `!67` 等）—— 按上文的问题跟踪工作流获取。
2. 用户作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名称或功能匹配的 PRD/规范文件。
4. 都未找到 → 询问用户规范在哪里；用户说没有 → **Spec** 子智能体跳过并报告“无可用规范”。

### 3. 识别标准来源

仓库中任何记录代码编写方式的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

### 4. 并行派发两个子智能体

按 `ReviewPr/references/review-protocol.md` 的“阶段 1：并行代理派发协议”执行：发送一条包含两个 `Agent` 工具调用的单条消息。两个子智能体均使用 `general-purpose`。

**标准子智能体提示** —— 包含：

- 完整的差异命令和提交列表。
- 第 3 步中找到的标准来源文件列表。
- 简要说明：“报告 —— 在相关文件/块中，差异违反已记录标准的每一个地方。引用标准（文件 + 规则）。区分硬性违反和判断性判断。跳过工具已强制执行的内容。不超过 400 字。”

**规范子智能体提示** —— 包含：

- 差异命令和提交列表。
- 规范的路径或已获取的内容。
- 简要说明：“报告：(a) 规范要求但缺失或仅部分实现的需求；(b) 差异中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现方式有误的需求。为每个发现引用规范中的对应行。不超过 400 字。”

规范缺失 → 跳过 Spec 子智能体，并在最终报告中注明。

### 5. 聚合

在两个标题 `## 标准` 和 `## 规范` 下，逐字或轻微整理后呈现两份报告。**不要**合并或重新排序发现 —— 两个轴刻意分离（见 _为什么有两个轴_）。

最后用一行总结：每个轴的发现总数，以及每个轴内的最严重问题（如果有）。不要在轴之间选择一个“赢家” —— 这正是分离要防止的那种重新排序。

## 为什么有两个轴

一次变更可能在一个轴上通过，在另一个轴上失败：

- 遵循每项标准但实现了错误内容的代码 → **标准通过，规范失败。**
- 完全按问题要求做了但打破了项目惯例的代码 → **规范通过，标准失败。**

分开报告防止一个轴掩盖另一个轴。
