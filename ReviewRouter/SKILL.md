# 请求代码审查（路由版）

本技能是"请求审查"的路由器：判定触发时机后，把评审派发给对应引擎执行，**不在本技能内自行展开评审模板**。评审引擎见下方路由表；本技能只负责"何时要审"与"派给谁"。

**核心原则：** 及早审查，频繁审查。

## 何时请求审查

**必须：**
- 在子智能体驱动的开发中，每个任务之后
- 完成主要功能之后
- 合并到主分支之前

**可选但有价值：**
- 卡住时（新鲜视角）
- 重构之前（基线检查）
- 修复复杂缺陷之后

## 路由表

| 场景 | 路由目标 | 用法 |
|---|---|---|
| 轻量流程关卡（需求对齐 + 声明验证 + 可以合并判定） | `ReviewPr --gate` | 派发 1 个 general-purpose 代理，模板见 `ReviewPr/references/gate-template.md` |
| 合并前缺陷聚焦评审（并行代理 + 置信度过滤） | `ReviewPr` | 阶段 0-3，可 `--fix` |
| 提交前代码质量润色（复用/简化/效率/抽象层次） | `PolishCode` | 并行 4 代理 + 应用修复 |
| 安全审计（OWASP 类） | `SecurityAudit` | 3 视角 + 严重性排序 |
| 编码规范 vs 规格符合度双轴评审 | `ReviewStandards` | 标准轴 + 规范轴 |
| 收到评审反馈后的处理 | `HandleReview` | 先验证，再实施 |

**路由依据：** 评审目标决定引擎——缺陷 → ReviewPr；质量 → PolishCode；安全 → SecurityAudit；标准/规格 → ReviewStandards；快速关卡 → ReviewPr --gate。多个维度同时需要时逐个按序加载执行。

## 派发要点（无论路由到哪个引擎）

1. **获取 git SHA：** `BASE_SHA=$(git rev-parse HEAD~1)`（或 `origin/main`）、`HEAD_SHA=$(git rev-parse HEAD)`。
2. **只读约束：** 评审代理在检出副本上只读，用 `git show`/`git diff`/`git log` 检查历史；需要其他修订版本时用 `git worktree add /tmp/review-[SHA] [SHA]`，永远不在检出副本上移动 HEAD。
3. **不传会话历史：** 给评审者精准构建的上下文（需求、计划、范围），永远不给整个会话历史——这能让评审者聚焦于工作产物，而不是你的思考过程。
4. **按反馈行动：** 立即修复严重问题，继续之前修复重要问题，次要问题稍后处理；评审者有误时用技术理由提出质疑（附上证据）。

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "我自己审查 diff 就行了，不用派发评审者" | 你是协调者 —— 内联审查 diff 会烧掉你用来继续推进工作所需的上下文窗口。派发评审子智能体：diff 和评估都在它的上下文中，只有评审结果回到你这里。 |
| "评审者需要我的整个会话历史才能理解这次变更" | 给它精准构建的上下文，永远不要给它你的会话历史。这能让评审者聚焦于工作产物，而不是你的思考过程。 |

## 危险信号

**永远不要：**
- 因为"它很简单"就跳过审查
- 忽视严重问题
- 在未修复重要问题的情况下继续
- 与有效的技术反馈争论
- 在本技能内手写评审模板自行评审（那是评审引擎的职责——直接路由）
