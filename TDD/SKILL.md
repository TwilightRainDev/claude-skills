# 测试驱动开发 (TDD)

## 概述

先写测试。看着它失败。然后写最少的代码让它通过。

**核心原则：** 如果你没有亲眼看到测试失败，你就无法确定它测试的是正确的事情。

**在字面上违反规则，就是在精神上违反规则。**

## 何时使用

**始终使用：**
- 新功能
- 错误修复
- 重构
- 行为变更

**例外（请询问你的结对伙伴）：**
- 一次性原型
- 生成代码
- 配置文件

心里想着“就这一次跳过 TDD”？停下来。那是在找借口。

## 铁律

> **没有先看到测试失败，就不写任何生产代码**

先写代码再写测试？删掉它。重新开始。

**没有例外：**
- 不要把它当作“参考”保留
- 不要在写测试时“改编”它
- 不要看它
- 删除就是删除

从测试开始全新实现。绝无例外。

## 红-绿-重构

循环：**红灯**（编写失败测试）→ **验证红灯**（亲眼看到它失败）→ **绿灯**（最简代码）→ **验证绿灯**（看到它通过）→ **重构**（保持绿色清理）→ 为下一个行为回到红灯。

关键分叉：
- 验证红灯时，失败原因不对（失败而非报错、非拼写错误）→ 回到红灯修测试
- 验证绿灯时未通过 → 修代码，不是改测试；其他测试挂掉 → 立刻修
- 重构后必须重新验证绿灯（保持绿色）

### 红灯 —— 编写失败测试

编写一个最小化的测试，说明应该发生什么。

<Good>
```typescript
test('失败操作重试 3 次', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```
命名清晰，测试真实行为，只测一件事
</Good>

<Bad>
```typescript
test('重试工作正常', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('success');
  await retryOperation(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});
```
命名模糊，测试的是模拟对象而非真实代码
</Bad>

**要求：**
- 只测一种行为
- 命名清晰
- 使用真实代码（除非迫不得已，否则不用模拟）

### 验证红灯 —— 看着它失败

**强制要求。永远不能跳过。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试失败（而不是报错）
- 失败信息符合预期
- 失败是因为功能缺失（而不是拼写错误）

**测试通过了？** 说明你在测试已有行为。修改测试。

**测试报错了？** 修复报错，重新运行，直到它正确失败。

### 绿灯 —— 最简代码

编写最简单的代码让测试通过。

<Good>
```typescript
async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('unreachable');
}
```
刚好够通过测试
</Good>

<Bad>
```typescript
async function retryOperation<T>(
  fn: () => Promise<T>,
  options?: {
    maxRetries?: number;
    backoff?: 'linear' | 'exponential';
    onRetry?: (attempt: number) => void;
  }
): Promise<T> {
  // 你并不需要它（YAGNI）
}
```
过度设计
</Bad>

不要添加功能、重构其他代码，或“改进”超出测试范围的东西。

### 验证绿灯 —— 看着它通过

**强制要求。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试通过
- 其他测试仍然通过
- 输出干净（无错误、无警告）

**测试没通过？** 修复代码，而不是改测试。

**其他测试失败了？** 现在就修复。

### 重构 —— 清理代码

仅在绿灯之后进行：
- 消除重复
- 改进命名
- 提取辅助函数

保持测试通过。不要添加新行为。

### 重复

为下一个功能编写下一个失败测试。

## 好的测试

| 质量 | 好的例子 | 不好的例子 |
|---------|------|---------|
| **最小化** | 只测一件事。名字里有“和”？拆分它。 | `test('验证邮箱和域名以及空白字符')` |
| **清晰** | 命名描述行为 | `test('test1')` |
| **表达意图** | 展示期望的 API | 掩盖代码应该做什么 |

在编写或修改任何测试时，请阅读 [writing-good-tests.md](writing-good-tests.md) 以获取保持测试诚实可靠的规则：
- 在编写测试之前，先说出哪个生产代码的改动会让这个测试失败
- 断言真实行为，绝不断言模拟对象的行为
- 将仅用于测试的代码放在测试工具中，不要放在生产类里
- 在模拟依赖之前，先理解它的副作用

## 常见借口

| 借口 | 事实 |
|--------|--------|
| “太简单了，不用测” | 简单的代码也会出错。写测试只要 30 秒。 |
| “我写完了再测” | 事后补写的测试会立即通过——这证明不了什么。它们可能测错了东西，可能测的是实现而非行为，可能漏掉了你忘记的边缘情况。你从未看着它失败，也就从未证明它能捕获那个 bug。先写测试强制你看到失败。 |
| “事后补写测试也能达到同样目标（精神大于仪式）” | 事后测试回答的是“这段代码做了什么？”；先写测试回答的是“这段代码应该做什么？”。事后写的测试会被你已经写好的代码带偏——你验证的是你记得的情况，而不是你本会发现的情况。覆盖率不能证明测试真的有用。 |
| “已经手动测过了” | 手动测试是随意的：没有记录你覆盖了什么，代码改动后无法重新运行，压力下容易漏掉用例。“我试过能用” ≠ 全面覆盖。自动化测试每次都以相同方式运行。 |
| “删掉花了好几小时写的代码是浪费” | 这是沉没成本谬误——无论如何那段时间已经花了。真正的选择是：用 TDD 重写（高置信度），还是保留代码并事后补测（低置信度，很可能有 bug）。留下你无法信任的代码才是浪费。 |
| “先留着当参考，我重新用 TDD 写” | 你一定会去改编它。那还是事后测试。删除就是删除。 |
| “我需要先探索一下” | 可以。探索完了就扔掉，然后用 TDD 重新开始。 |
| “测试很难写 = 设计不清晰” | 倾听测试的声音。难测 = 难用。 |
| “TDD 会拖慢我” | TDD 恰恰是务实的路径：在提交前捕获 bug，防止回归，让你无畏地重构。“务实”的捷径意味着在生产环境调试——更慢，而不是更快。 |
| “手动测试更快” | 手动测试不能证明边缘情况。每次改动你都要重新测。 |
| “现有代码没有测试” | 你正在改进它。为现有代码添加测试。 |

## 危险信号 —— 停下来，重新开始

- 先写代码再写测试
- 实现之后再写测试
- 测试立即通过了
- 无法解释测试为什么失败
- 测试“以后”补上
- 找借口“就这一次”
- “我已经手动测过了”
- “事后补测也能达到同样目的”
- “重要的是精神而不是仪式”
- “先保留作为参考”或“改编现有代码”
- “已经花了很多时间，删掉太浪费”
- “TDD 太教条，我这是务实”
- “这次情况不一样……”

**上述任何一条都意味着：删掉代码。用 TDD 重新开始。**

## 示例：错误修复

**Bug：** 空邮箱被接受

**红灯**
```typescript
test('拒绝空邮箱', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
```

**验证红灯**
```bash
$ npm test
FAIL: 期望得到 'Email required'，实际得到 undefined
```

**绿灯**
```typescript
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Email required' };
  }
  // ...
}
```

**验证绿灯**
```bash
$ npm test
PASS
```

**重构**
如果有多个字段需要验证，提取验证逻辑。

## 验证清单

在标记工作完成之前：

- [ ] 每个新函数/方法都有测试
- [ ] 每个测试在实现前都亲眼看过它失败
- [ ] 每个测试失败的原因都符合预期（功能缺失，而不是拼写错误）
- [ ] 为通过每个测试只写了最少的代码
- [ ] 所有测试通过
- [ ] 输出干净（无错误、无警告）
- [ ] 测试使用真实代码（除非迫不得已，否则不用模拟）
- [ ] 覆盖了边缘情况和错误路径

有没有哪一项勾不上？那你跳过了 TDD。重新开始。

## 卡住时怎么办

| 问题 | 解决办法 |
|---------|----------|
| 不知道如何测试 | 写下你期望的 API。先写断言。向你的结对伙伴求助。 |
| 测试太复杂 | 设计太复杂。简化接口。 |
| 什么都要模拟 | 代码耦合太紧。使用依赖注入。 |
| 测试准备代码太多 | 提取辅助函数。仍然复杂？简化设计。 |

## 调试集成

发现 bug？先写一个能复现它的失败测试。然后走 TDD 循环。这个测试既能证明修复，又能防止回归。

永远不要在没有测试的情况下修复 bug。

## 最终规则

> **生产代码 → 必须有测试，并且这个测试曾经失败过。否则 → 就不是 TDD。**

未经你的结对伙伴允许，没有任何例外。


# 编写良好测试

**在以下情况加载此参考：** 编写或修改测试、添加模拟（mock）、或为测试添加清理/辅助方法时。

## 概述

测试的存在是为了捕获特定的故障。这里的一切由两条原则支配：

```
1. 每个测试都要指明它能捕获的故障
2. 每个测试都要对真实内容进行演练
```

严格的 TDD 会自然地产出这两者：先编写测试并在真实代码上观察其失败，就已经证明了它能失败；只有当真实依赖被证明为缓慢或外部依赖时，才值得引入模拟。

## 原则 1：指明故障

在编写测试体之前，先回答：**什么样的生产代码变更会让这个测试失败——这个变更是缺陷（bug）还是决策（decision）？** 一个测试之所以有价值，是因为它能捕获错误分支、遗漏的副作用、错误的参数、边界情况或破损的契约。

**独立推导预期结果。** 使用字面量和手工核对的夹具（fixture）；表驱动测试（table-driven tests）中带有字面量 `want` 值是首选形态。由被测代码或其辅助函数计算出的预期值，无论代码做什么都会通过：

```typescript
// [FAIL] 镜像断言：同一个构造器计算两边——永远为真
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// [OK] 手工推导的字面量
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**不做变更检测器。** 如果只有人为决策才能使测试失败——例如常量的值、精确的消息措辞、私有结构——那么它会在重新设计时失败，而在缺陷面前却无动于衷。测试依赖该决策的行为，而不是决策本身：不要写 `expect(MAX_RETRIES).toBe(5)`，而应该写“一次失败的调用会被重试 5 次，第 6 次尝试永远不会发生”。

**测试行为，而非文本。** 断言某个脚本、技能或配置包含某行精确内容，只能证明“源就是源”。应在受控输入下运行脚本，并断言输出、副作用或退出码。用于指导智能体的文档，应通过消费该智能体的行为来测试（参见 `ManageSkills`，它评估了技能措辞）；面向人类的散文则根本不需要测试。

**测试你的代码，而不是框架。** 测试你的代码在其边界处对外提供的契约——你注册的路由、你发出的查询、你生成的有效载荷。上层机制是它们维护者自己要写的测试（经典的例子：断言路由器会调用注册的处理程序——这是框架的测试，不是你的）。当上层行为确实让你感到意外时，写一个窄窄的特征化测试来指明该假设。同样的边界也适用于你代码内部：构造器、getter、常量和简单的转发函数，只有在它们执行校验、规范化、默认值、推导、强制或引发副作用时才需要测试——否则，直接断言第一个依赖它们的、面向消费者的可见结果即可。

### 关卡函数

在编写测试体之前：

- 指出能让这个测试失败的生产代码变更。
- 无法指出任何一个 → 重新设计，围绕一个可观察的行为
- "源代码文本变了" → 运行该构件并断言其效果
- 只有人为决策 → 这是变更检测器；测试依赖该决策的行为
- 确认预期值不是用被测代码推导的；如果它复用了被测代码的逻辑或辅助函数，替换为字面量或手工核对的夹具

## 原则 2：对真实内容进行演练

**模拟本身不应获得任何断言。** 模拟断言在模拟存在时通过，在模拟不存在时失败——它说明不了组件本身。请断言真实组件的行为；如果你正在检查的正是模拟本身，那就取消模拟或删除该断言。

```typescript
// [OK] 真实行为
expect(screen.getByRole('navigation')).toBeInTheDocument();

// [FAIL] 模拟的存在性
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**你的人类伙伴的纠正：** “我们是在测试一个模拟的行为吗？”

**在正确的层级进行模拟。** 在替换真实方法之前，先了解它的所有副作用；只模拟慢速或外部操作，而保留测试所依赖的真实部分。如果不确定，先针对真实实现运行测试，观察实际需要发生什么。

```typescript
// [FAIL] 模拟吞掉了重复检测所依赖的配置写入
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// [OK] 只模拟慢速的服务器启动；配置写入保持真实
vi.mock('MCPServerManager');
```

**让测试替身具体化。** 当参数、调用次数或调用顺序属于契约的一部分时，请断言它们——一个接受任何内容的伪造者验证不了任何东西。为每个分支（成功、错误、畸形）提供自己的夹具或间谍（spy），使得错误分支无法满足预期。

**完整地镜像真实数据。** 模拟的响应结构应完全按照现实中的完整结构——包含所有已文档化的字段——而不仅仅是你的测试读取的那些。部分模拟会在下游代码读取到遗漏字段时静默失败：测试通过，而集成却崩溃。

**生产类只携带生产方法。** 只有测试才需要的清理逻辑应放在测试工具中，绝不要以 `destroy()` 这样的方法出现在生产类上。问：这个方法是否仅在测试中被调用？这个类是否拥有该资源的生命周期？答案不对 → 就应放在测试工具中。

**优先使用真实组件，而非复杂的模拟。** 当模拟设置超出测试逻辑本身、模拟缺少真实组件拥有的方法、或测试因模拟变更而失败时，应切换为使用真实组件的集成测试。**你的人类伙伴的问题：** “我们真的需要用模拟吗？”

### 关卡函数

在添加模拟或测试辅助函数之前：

- 列出真实方法的所有副作用；保留测试所依赖的真实部分——在其之下的慢速/外部层级进行模拟。
- 模拟响应应完整镜像真实结构。
- 只在测试中被调用的方法应放在测试工具中，而非生产代码里。
- 即将要对模拟本身进行断言？取消模拟，或删除该断言。

## 测试随实现一起交付

TDD 周期——失败测试、最小实现、重构——就是“完成”的含义。交付行为所需的测试，并且只交付这些：琐碎代码和人类散文不需要测试，而为应付流程而写的测试将永久地增加维护成本。

## 变异检查

在结束之前，对生产代码进行心理上的变异；至少应有一个测试能针对每种现实的变异失败：

- 错误的常量或参数
- 错误的分支处理
- 遗漏的状态变更或副作用
- 空返回值或默认返回值
- 对零值、空值、空切片、未授权或畸形输入缺少校验

若没有任何变异被捕获，说明该行为未被保护——或者该测试是同义反复。

## 快速参考

| 当你... | 做... |
|---------|-------|
| 编写任何测试 | 指明它能捕获的故障——即一个缺陷，而非一个决策 |
| 构造预期值 | 手工推导；绝不使用被测代码 |
| 测试脚本或文档 | 运行它 / 对它的消费者进行压力测试；绝不 grep 其文本内容 |
| 要测试一个依赖 | 测试你边界上的契约，而不是它们已文档化的机制 |
| 要断言一个被模拟的元素 | 测试真实组件，或者取消模拟 |
| 即将模拟一个方法 | 了解其副作用；在慢速/外部层级进行模拟 |
| 构造模拟响应 | 完整镜像真实结构 |
| 需要只有测试才用的清理逻辑 | 放在测试工具中 |
| 发现模拟设置膨胀 | 切换为使用真实组件的集成测试 |
| 完成一个测试文件 | 执行变异检查 |

## 警告信号

- 设置和断言共享同一个对象，从而保证相等性
- 测试只能通过 panic、崩溃或缺失选择器来失败
- 测试在每次有意的变更时都失败，却从不在意外的破坏时失败
- 预期值隐藏在循环、构造器或辅助函数后面
- 测试 grep 源代码文本，或断言一个被删除的符号保持被删除
- 即便只剩下框架，该测试仍然“有用”
- 测试仅为覆盖率而存在，没有检查任何副作用或结果
- 断言检查了 `*-mock` 这样的测试 ID，或者如果移除模拟就会失败
- 某个方法只在测试文件中被调用
- 模拟设置占测试的一半以上，或者你无法解释为什么需要模拟
- 模拟“只是为了安全”
