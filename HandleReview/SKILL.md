# HandleReview（代码审查接收）

代码审查需要技术评估，而非情绪表演：收到反馈后先技术验证，再实施。**核心原则：先验证，再实施；先询问，再假设；技术正确性优先于社交舒适。**

## 何时使用

- 收到代码审查反馈（合作伙伴、外部审查者、PR 评论），准备动手实施之前。
- 反馈中有任何一项理解不明确。
- 打算质疑或反驳某条建议之前。

## 回应顺序

收到反馈时按序执行，不跳步：

| # | 动作 | 内容 |
|---|---|---|
| 1 | 阅读 | 完整看完反馈，不做反应 |
| 2 | 理解 | 用自己的话复述需求（或询问） |
| 3 | 验证 | 对照代码库的现实进行检查 |
| 4 | 评估 | 在当前代码库中技术上是否合理 |
| 5 | 回应 | 技术性确认或有理由的质疑 |
| 6 | 实施 | 一次一项，每项都测试 |

## 禁止的回应

永远不要：

- “您完全正确！”（明确违反指令文件）
- “好观点！” / “很棒的反馈！”（表演性）
- “我现在就实施”（在验证之前）
- 任何感谢表达

应当：

- 复述技术需求
- 提出澄清性问题
- 有技术理由时提出质疑
- 直接开始工作（行动大于言语）

## 反馈不明确时

任何一项不明确 → **停止，先不要实施任何内容，请求澄清不明确的项目。**

原因：项目之间可能相互关联。部分理解 = 错误实施。

> 你的合作伙伴：“修复第 1-6 项”
> 你理解 1、2、3、6。第 4、5 项不清楚。
> [错误] 现在实施 1、2、3、6，稍后询问 4、5
> [正确] “我理解第 1、2、3、6 项。在继续之前需要澄清第 4 和第 5 项。”

## 来源特定处理

### 来自合作伙伴

- 可信赖——理解后实施。
- 范围不明确时仍需询问。
- 不要表演性赞同。
- 直接行动或技术性确认。

### 来自外部审查者

实施之前逐项检查：

| # | 检查项 |
|---|---|
| 1 | 对于当前代码库在技术上正确吗？ |
| 2 | 会破坏现有功能吗？ |
| 3 | 当前实施的原因是什么？ |
| 4 | 在所有平台/版本上都能工作吗？ |
| 5 | 审查者了解完整上下文吗？ |

- 建议似乎有误 → 用技术理由提出质疑。
- 无法轻易验证 → 直接说明：“没有 [X] 我无法验证。我应该 [调查/询问/继续] 吗？”
- 与合作伙伴之前的决定冲突 → 先停下来与你的合作伙伴讨论。

规则：“外部反馈——保持怀疑，但仔细检查”。

## YAGNI 检查

审查者建议“正确实施”某功能时 → 在代码库中 grep 实际使用情况：

- 未使用 → 问：“这个端点没有被调用。删除它（YAGNI）？”
- 已使用 → 正确实施。

> 审查者：“实现适当的指标追踪，包含数据库、日期筛选、CSV 导出”
> [正确] “grep 了代码库——没有任何东西调用这个端点。删除它（YAGNI）？还是说有我遗漏的使用场景？”

规则：“你和审查者都向我汇报。如果我们不需要这个功能，就不要添加它。”

## 实施顺序

1. 先澄清任何不明确的内容。
2. 然后按此顺序实施：阻塞性问题（崩溃、安全）→ 简单修复（拼写、导入）→ 复杂修复（重构、逻辑）。
3. 逐项测试每个修复。
4. 验证没有回归。

## 何时提出质疑

| 触发条件 |
|---|
| 建议破坏了现有功能 |
| 审查者缺乏完整上下文 |
| 违反了 YAGNI（未使用的功能） |
| 对于当前技术栈在技术上不正确 |
| 存在遗留/兼容性原因 |
| 与合作伙伴的架构决策冲突 |

如何质疑：

- 使用技术理由，而非防御性态度。
- 提出具体问题。
- 引用能正常工作的测试/代码。
- 架构性问题 → 请你的合作伙伴介入。
- 不习惯公开质疑 → 说出这种紧张感，然后向你的合作伙伴说明你发现的问题。

> 审查者：“移除遗留代码”
> [错误] “您完全正确！我马上移除……”
> [正确] “检查中……构建目标是 10.15+，这个 API 需要 13+。需要遗留代码以保持向后兼容。当前实现的 bundle ID 有误——是修复它还是放弃对 13 以下版本的支持？”

## 承认正确的反馈

反馈确实正确时：

> [正确] “已修复。[简要描述修改了什么]”
> [正确] “好眼力——[具体问题]。已在 [位置] 修复。”
> [正确] [直接修复并在代码中展示]
>
> [错误] “您完全正确！”
> [错误] “好观点！”
> [错误] “感谢指出！”
> [错误] “感谢 [任何内容]”
> [错误] 任何感谢表达

不用感谢的原因：行动胜于言语，直接修复即可，代码本身就能表明你听到了反馈。

正要写“感谢”时 → 删除它，改为陈述修复内容。

## 纠正自己的质疑

质疑错了时：

> [正确] “你是对的——我检查了 [X]，它确实 [Y]。现在实施。”
> [正确] “验证过了，你是正确的。我最初的理解错了，因为 [原因]。正在修复。”
>
> [错误] 长篇道歉
> [错误] 为自己质疑辩护
> [错误] 过度解释

实事求是地陈述更正，然后继续。

## 常见错误

| 错误 | 修复 |
|---|---|
| 表演性赞同 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 不测试就批量处理 | 逐项处理，逐项测试 |
| 假设审查者是对的 | 检查是否会破坏东西 |
| 避免质疑 | 技术正确性 大于 舒适 |
| 部分实施 | 先澄清所有项目 |
| 无法验证但仍继续 | 说明局限，请求方向 |

## GitHub 线程回复

在 GitHub 上回复行内审查评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为 PR 顶层评论。
