# WritePlan

## 概述

一个技能，一个输出：一份可执行的实施计划。三种输入模式：

| 模式 | 输入 | 产出 |
|---|---|---|
| **规格说明合成** | 对话中讨论过的需求，尚无规格说明 | 规格说明或PRD（无访谈 —— 综合讨论过的内容）加 主动提供编写实施计划 |
| **重构计划** | 用户想规划一次重构 或 重构 RFC 或 安全的增量步骤 | 访谈 → 验证仓库 → 小提交计划 → GitHub issue |
| **实施计划** | 已有规格说明或需求文档 | 零上下文可执行计划（文件、接口、细粒度 TDD 步骤） |

**核心原则：** 假定实施者对代码库零上下文且品味可疑。记录他们需要知道的一切：每个任务涉及哪些文件、代码、测试、需查阅的文档、如何测试。将整个计划分解为细粒度任务。DRY。YAGNI。TDD。频繁提交。

**在开始时宣布：** “我正在使用 WritePlan 技能来创建计划。”

**将计划保存到：** `docs/plans/YYYY-MM-DD-<feature-name>.md`（用户对计划位置的偏好可覆盖此默认路径）。

**上下文：** 如果在隔离的工作树中工作，应在执行时通过 `using-git-worktrees` 技能创建。

## 1. 模式选择

- 用户说“把它变成规格说明或PRD”或讨论了需求但尚无规格说明 → **规格说明合成**
- 用户说“规划一次重构” 或 “重构 RFC” 或 “安全的增量步骤” → **重构计划**
- 已存在规格说明或需求文档且需要实施计划 → **实施计划**

## 2. 澄清策略

- **规格说明合成：** 不要访谈用户 —— 综合已知信息。仅确认你无法推导的内容：如果未提供词汇，需确认规格说明应发布到哪里（仓库、跟踪器或纯文本文件），以及测试接缝是否符合他们的期望。
- **实施计划：** 不需要访谈 —— 规格说明是事实来源。如果规格说明涵盖多个独立子系统，则应在头脑风暴阶段已分解为子项目规格说明；如果未分解，建议拆分为多个计划 —— 每个子系统一个。每个计划都应能独立产生可工作、可测试的软件。
- **重构计划：** 访谈用户 —— 你可以跳过你认为不必要的步骤：
  1. 询问对问题的详细描述以及任何潜在的解决方案想法。
  2. 询问他们是否考虑过其他选项，并呈现其他选项。
  3. 就实施进行访谈。要极其详细和彻底。
  4. 敲定确切范围 —— 计划变更的内容和计划不变更的内容。

## 3. 探索代码库

验证假设并理解当前状态。在整个过程中使用项目的领域术语表词汇；尊重你所触及区域中的任何 ADR。

- **规格说明合成：** 勾勒你将要测试该功能的接缝。应优先使用现有接缝而非新接缝。使用尽可能高的接缝；如果需要新接缝，在你能做到的最高点提出。代码库中的接缝越少越好 —— 理想数量是一个。与用户确认这些接缝符合他们的期望。
- **重构计划：** 在代码库中查找该区域的测试覆盖率。如果覆盖率不足，询问用户的测试计划。
- **实施计划：** 规划将创建或修改哪些文件以及各自负责什么（参见下面的文件结构）。遵循现有代码库中的既定模式；如果你正在修改的文件已变得臃肿，在计划中纳入拆分是合理的。

## 4. 生成文档

使用下面的统一模板。一个零上下文的实施者必须能不问问题地执行它。

<plan-template>

# [功能名称] 实施计划

> **对于执行者：** 必需子技能：使用 SubagentDrivenDev（推荐）或 ExecutingPlans 逐任务实施此计划。步骤使用复选框（`- [ ]`）语法进行跟踪。

**目标：** [一句话描述构建内容]

**架构：** [2-3 句关于方法]

**技术栈：** [关键技术或库]

## 问题陈述

用户面临的问题，从用户视角描述。

## 解决方案

问题的解决方案，从用户视角描述。

## 用户故事

一个长编号列表的用户故事，格式如下：
1. 作为 <角色>，我想要 <功能>，以便 <收益>

此列表应极其详尽，覆盖功能的所有方面。*（仅规格说明合成模式。）*

## 全局约束

规格说明中的项目级需求 —— 版本基线、依赖限制、命名和文案规则、平台要求 —— 每行一条，精确复制规格说明中的值。每个任务的约束都隐式包含本节内容。

## 提交 或 任务

计划本身。用通俗英语编写，将实施分解为尽可能小的提交或任务。每个提交或任务都应使代码库保持可工作状态（Martin Fowler：“让每个重构步骤尽可能小，以便你始终能看到程序在运行”）。使用下面“任务结构”中的任务结构。

## 决策文档

所做实施决策的列表。可包括：

- 将要构建或修改的模块
- 将要修改的模块接口
- 来自开发者的技术澄清
- 架构决策
- 模式变更
- API 契约
- 特定交互

不要包含具体文件路径或代码片段。它们可能很快过时。

例外：如果原型产生了比散文更精确编码决策的片段（状态机、reducer、模式、类型形状），将其内联到相关决策中，并简要注明来自原型。裁剪到决策密集部分 —— 不是工作演示，只是重要部分。

## 测试决策

所做测试决策的列表。包括：

- 什么构成好的测试（仅测试外部行为，不测试实现细节）
- 哪些模块将被测试
- 测试的先例（即代码库中类似类型的测试）

## 范围之外

此计划中不在范围内的内容描述。

## 进一步说明

关于功能的任何进一步说明。

</plan-template>

### 文件结构

在定义任务之前，规划将创建或修改哪些文件以及各自负责什么。分解决策在此被锁定。

- 设计边界清晰、接口定义良好的单元。每个文件应有一个明确的职责。
- 你能最好地推理一次能容纳在上下文中的代码，当文件聚焦时修改也更可靠。优先选择更小、聚焦的文件，而非做过多的巨大文件。
- 一起变更的文件应放在一起。按职责拆分，而非按技术层。
- 在现有代码库中，遵循既定模式。如果代码库使用大文件，不要单方面重构 —— 但如果你正在修改的文件已变得臃肿，在计划中纳入拆分是合理的。

此结构为任务分解提供依据。每个任务应产生独立可理解的、自包含的变更。

### 任务粒度

任务是承载自己测试周期且值得一个独立评审关卡的最小单元。在划定任务边界时：将设置、配置、脚手架和文档步骤折叠到需要它们交付物的任务中；仅当评审者可能有意义地拒绝一个任务而批准其相邻任务时才拆分。每个任务以独立可测试的交付物结束。

### 细粒度任务粒度

**每一步是一个动作（2-5 分钟）：**
- “编写失败的测试” —— 一步
- “运行它以确认失败” —— 一步
- “编写让测试通过的最小代码” —— 一步
- “运行测试并确认通过” —— 一步
- “提交” —— 一步

### 任务结构

````markdown
### 任务 N：[组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：[此任务从之前任务使用的内容 —— 精确签名]
- 产出：[后续任务依赖的内容 —— 精确函数名、参数和返回类型。任务的实施者只看到自己的任务；此块是他们了解相邻任务使用的名称和类型的方式]

- [ ] **步骤 1：编写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试以确认失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL，提示“function not defined”

- [ ] **步骤 3：编写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试以确认通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: 添加特定功能"
```
````

### 无占位符

每一步都必须包含工程师所需的实际内容。这些是**计划失败** —— 永远不要写它们：
- “TBD”、“TODO”、“稍后实现”、“补充细节”
- “添加适当的错误处理” 或 “添加验证” 或 “处理边缘情况”
- “为上述内容编写测试”（没有实际测试代码）
- “类似于任务 N”（重复代码 —— 工程师可能按顺序阅读任务）
- 描述要做什么但不展示如何做的步骤（代码步骤需要代码块）
- 引用任何任务中未定义的类型、函数或方法

## 5. 自审

在编写完整计划后，用全新眼光审视规格说明，并对照它检查计划。这是你自己运行的检查清单 —— 不是派发子智能体。清单的权威版本见 `references/spec-self-review.md`（本文件为权威宿主）。

**1. 规格说明覆盖：** 浏览规格说明中的每个章节或需求。你能指出一个实现它的任务吗？列出任何缺口。

**2. 占位符扫描：** 在你的计划中搜索危险信号 —— 上面“无占位符”部分中的任何模式。修复它们。

**3. 类型一致性：** 你在后续任务中使用的类型、方法签名和属性名称是否与你在早期任务中定义的一致？在任务 3 中称为 `clearLayers()` 但在任务 7 中称为 `clearFullLayers()` 的函数是一个缺陷。

如果发现问题，就地修复。无需重新审阅 —— 只需修复并继续。如果发现规格说明需求没有对应任务，添加任务。

## 6. 发布

- **本地计划文件：** 保存到 `docs/plans/YYYY-MM-DD-<feature-name>.md`（或用户偏好的位置）。
- **问题跟踪器：** 如果用户希望计划发布到跟踪器（或已提供跟踪器词汇），创建包含计划的 GitHub issue 并应用 `ready-for-agent` 分流标签 —— 无需额外分流。问题跟踪器和分流标签词汇应已提供 —— 如果未提供，询问用户计划应发布到哪里。

## 7. 执行交接

保存计划后，提供执行选择：

**“计划已完成并保存到 `docs/plans/<filename>.md`。两种执行选项：**

**1. 子智能体驱动（推荐）** —— 每个任务派发全新子智能体，任务间评审，快速迭代

**2. 内联执行** —— 在当前会话中使用 ExecutingPlans 执行任务，批量执行并设置检查点

**选择哪种？”**

**如果选择子智能体驱动：**
- **必需子技能：** 使用 SubagentDrivenDev
- 每个任务全新子智能体 加 两阶段评审

**如果选择内联执行：**
- **必需子技能：** 使用 ExecutingPlans
- 带检查点的批量执行，供评审时使用
