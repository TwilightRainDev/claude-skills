# WritePlan

把需求、重构意图或规格转成一份可执行的实施计划。三种输入模式，输出同一份计划。

## 何时使用

| 模式 | 输入 | 产出 |
|---|---|---|
| **规格说明合成** | 对话中讨论过的需求，尚无规格说明 | 规格说明或 PRD（无访谈 —— 综合讨论过的内容），并主动提供编写实施计划 |
| **重构计划** | 用户想规划一次重构、重构 RFC 或安全的增量步骤 | 访谈 → 验证仓库 → 小提交计划 → GitHub issue |
| **实施计划** | 已有规格说明或需求文档 | 零上下文可执行计划（文件、接口、细粒度 TDD 步骤） |

**核心原则：** 假定实施者对代码库零上下文且品味可疑。记录他们需要知道的一切：每个任务涉及哪些文件、代码、测试、需查阅的文档、如何测试。将整个计划分解为细粒度任务。DRY。YAGNI。TDD。频繁提交。

**在开始时宣布：** “我正在使用 WritePlan 技能来创建计划。”

**将计划保存到：** `docs/plans/YYYY-MM-DD-<feature-name>.md`（用户对计划位置的偏好可覆盖此默认路径）。

**上下文：** 如果在隔离的工作树中工作，应在执行时创建隔离工作区：优先使用工具集自带的 worktree 命令（例如 `EnterWorktree`），否则用 `git worktree add` 在 .worktrees/ 下创建一个，或确认现有工作区。

## 1. 模式选择

- 用户说“把它变成规格说明或PRD”或讨论了需求但尚无规格说明 → **规格说明合成**
- 用户说“规划一次重构”或“重构 RFC”或“安全的增量步骤” → **重构计划**
- 已存在规格说明或需求文档且需要实施计划 → **实施计划**

## 2. 澄清策略

- **规格说明合成：** 不要访谈用户 —— 综合已知信息。仅确认你无法推导的内容：如果未提供词汇，需确认规格说明应发布到哪里（仓库、跟踪器或纯文本文件），以及测试接缝是否符合他们的期望。
- **实施计划：** 不需要访谈 —— 规格说明是事实来源。如果规格说明涵盖多个独立子系统，则应在头脑风暴阶段已分解为子项目规格说明；如果未分解，向用户提出拆分为多个计划 —— 每个子系统一个。每个计划都应能独立产生可工作、可测试的软件。
- **重构计划：** 访谈用户，按以下四步走；某步与本项目无关时，说明理由再跳过：
  1. 询问对问题的详细描述以及任何潜在的解决方案想法。
  2. 询问他们是否考虑过其他选项，并呈现其他选项。
  3. 就实施进行访谈。要极其详细和彻底。
  4. 敲定确切范围 —— 计划变更的内容和计划不变更的内容。

## 3. 探索代码库

验证假设并理解当前状态。在整个过程中使用项目的领域术语表词汇；尊重你所触及区域中的任何 ADR。

- **规格说明合成：** 勾勒你将要测试该功能的接缝。优先使用现有接缝而非新接缝。使用尽可能高的接缝；如果需要新接缝，在你能做到的最高点提出。代码库中的接缝越少越好 —— 理想数量是一个。与用户确认这些接缝符合他们的期望。
- **重构计划：** 在代码库中查找该区域的测试覆盖率。如果覆盖率不足，询问用户的测试计划。
- **实施计划：** 规划将创建或修改哪些文件以及各自负责什么（参见下面的文件结构）。遵循现有代码库中的既定模式；如果你正在修改的文件已变得臃肿，在计划中纳入拆分是合理的。

## 4. 生成文档

使用 `references/plan-template.md` 的统一模板。一个零上下文的实施者必须能不问问题地执行它。

### 文件结构

在定义任务之前，规划将创建或修改哪些文件以及各自负责什么。分解决策在此被锁定。

- 设计边界清晰、接口定义良好的单元。每个文件应有一个明确的职责。
- 你能最好地推理一次能容纳在上下文中的代码，当文件聚焦时修改也更可靠。优先选择更小、聚焦的文件，而非做过多的巨大文件。
- 一起变更的文件应放在一起。按职责拆分，而非按技术层。
- 在现有代码库中，遵循既定模式。如果代码库使用大文件，不要单方面重构 —— 但如果你正在修改的文件已变得臃肿，在计划中纳入拆分是合理的。

此结构为任务分解提供依据。每个任务应产生独立可理解的、自包含的变更。

### 任务粒度

任务是承载自己测试周期且值得一个独立评审关卡的最小单元。在划定任务边界时：将设置、配置、脚手架和文档步骤折叠到需要它们交付物的任务中；仅当评审者可能有意义地拒绝一个任务而批准其相邻任务时才拆分。每个任务以独立可测试的交付物结束。

### 细粒度任务粒度

**每一步是一个动作（2-5 分钟）：**
- “编写失败的测试” —— 一步
- “运行它以确认失败” —— 一步
- “编写让测试通过的最小代码” —— 一步
- “运行测试并确认通过” —— 一步
- “提交” —— 一步

### 任务结构

任务条目模板（文件/接口/细粒度步骤五段式）见 `references/plan-template.md` 的「任务结构」一节。

### 无占位符

每一步都必须包含工程师所需的实际内容。这些是**计划失败** —— 永远不要写它们：
- “TBD”、“TODO”、“稍后实现”、“补充细节”
- “添加适当的错误处理”或“添加验证”或“处理边缘情况”
- “为上述内容编写测试”（没有实际测试代码）
- “类似于任务 N”（重复代码 —— 工程师可能按顺序阅读任务）
- 描述要做什么但不展示如何做的步骤（代码步骤需要代码块）
- 引用任何任务中未定义的类型、函数或方法

## 5. 自审

在编写完整计划后，用全新眼光审视规格说明，并对照它检查计划。这是你自己运行的检查清单 —— 不是派发子智能体。清单的权威版本见 `references/spec-self-review.md`（本文件为权威宿主）。

**1. 规格说明覆盖：** 浏览规格说明中的每个章节或需求，指出实现它的任务。指不出的即为缺口，列出来。

**2. 占位符扫描：** 在你的计划中搜索危险信号 —— 上面“无占位符”部分中的任何模式。修复它们。

**3. 类型一致性：** 你在后续任务中使用的类型、方法签名和属性名称是否与你在早期任务中定义的一致？在任务 3 中称为 `clearLayers()` 但在任务 7 中称为 `clearFullLayers()` 的函数是一个缺陷。

如果发现问题，就地修复。无需重新审阅 —— 只需修复并继续。如果发现规格说明需求没有对应任务，添加任务。

## 6. 发布

- **本地计划文件：** 保存到 `docs/plans/YYYY-MM-DD-<feature-name>.md`（或用户偏好的位置）。
- **问题跟踪器：** 如果用户希望计划发布到跟踪器（或已提供跟踪器词汇），创建包含计划的 GitHub issue 并应用 `ready-for-agent` 分流标签 —— 无需额外分流。问题跟踪器和分流标签词汇应已提供 —— 如果未提供，询问用户计划应发布到哪里。

## 7. 执行交接

保存计划后，提供执行选择：

> **计划已完成并保存到 `docs/plans/<filename>.md`。两种执行选项：**
>
> **1. 子智能体驱动（推荐）** —— 每个任务派发全新子智能体，任务间评审，快速迭代
>
> **2. 内联执行** —— 在当前会话中使用 ExecutingPlans 执行任务，批量执行并设置检查点
>
> **选择哪种？**

**如果选择子智能体驱动：**
- **必需子技能：** 使用 SubagentDrivenDev
- 每个任务全新子智能体 + 两阶段评审

**如果选择内联执行：**
- **必需子技能：** 使用 ExecutingPlans
- 带检查点的批量执行，供评审时使用
