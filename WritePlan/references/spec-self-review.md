# 规格/计划自审清单（spec-self-review）

规格说明（设计文档）与实施计划在成文后的自审清单。两处应用：**ProbeIntent**（规格说明自审）、**WritePlan**（计划自审）。权威宿主为 `WritePlan`。

自审是派发者自己运行的检查——不派子代理，就地修复，不需要重新审阅。

## 四步检查

### 1. 占位符扫描

搜索以下危险信号并修复（这是**文档缺陷**，永远不要写下它们）：

- "TBD"、"TODO"、"稍后实现"、"补充细节"
- "添加适当的错误处理" / "添加验证" / "处理边缘情况"（无具体内容）
- "为上述内容编写测试"（没有实际测试代码）
- "类似于任务 N"（重复代码——读者可能按顺序阅读）
- 描述要做什么但不展示如何做的步骤（代码步骤需要代码块）
- 引用任何前文未定义的类型、函数或方法

### 2. 内部一致性

- 章节之间是否有矛盾？架构是否与功能描述匹配？
- 后续任务中使用的类型、方法签名、属性名是否与早期任务中定义的一致？（例：任务 3 称 `clearLayers()`，任务 7 称 `clearFullLayers()` 是缺陷）
- 范围检查：是否足够聚焦以适合单一实施计划，还是需要分解为子项目？

### 3. 歧义检查

- 是否有任何需求可能被以两种不同方式解释？如果有，选择一个并明确说明。
- 用户故事中的角色/受益是否可验证？

### 4. 覆盖检查（规格 vs 计划）

- 浏览规格说明中的每个章节或需求。能指出一个实现它的任务吗？列出缺口。
- 发现规格需求没有对应任务 → 添加任务。
- 发现计划引用了规格中不存在的内容 → 移除或标注。

## 快速参考

| 发现 | 处理 |
|---|---|
| TBD/TODO/占位符 | 就地填实，或删除该步骤 |
| 两处定义不一致 | 统一为较早定义并全篇替换 |
| 需求无对应任务 | 添加任务 |
| 任务可被两种方式理解 | 写明取舍，显式选择一个 |
| 单一计划塞多子系统 | 拆分为独立计划，各可独立交付 |
